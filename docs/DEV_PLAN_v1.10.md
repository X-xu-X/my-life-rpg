## 〇、总原则（必须遵守）

1. **数据红线**：`game_of_life.db` 是真实生活数据，**禁止物理删除**；新增表走 `create_all`、加列走 `migrate_schema`；任何批量操作前**先整库备份到 `backups/`**。
2. **兼容过渡**：老数据必须容忍新字段为空。新字段一律可空或无破坏默认值；**已结算的历史记录不得被重算**。
3. **一个 commit = 一个逻辑单元**，中文 message `类型: 简述`（如 `feat(P0-1): 挑战奖励改由 AI 主导定价`）。
4. **一致性铁律**（v1.5 B-03 教训，不得违反）：
   - 金币只有 `coin_service.grant()` 一个写入口
   - 属性值写入统一走 `judge_service._clamp_attribute_value`
   - 挑战加点必须复用 `judge_service.confirm()`
   - 任何"更新"语义**不得用"先删后建"实现**
5. **【本轮作废的旧铁律】**：v1.8 立的「**金币金额必须由 `COIN_TABLE` 派生、AI 只得给 difficulty**」——**P0-1 起作废**（用户 2026-09-29 确认"完全放开给 AI 定价"）。`COIN_TABLE` 降级为**解析兜底表**（AI 给不出合法数字时才用），不再是唯一权威。执行者**不要**在代码里加"金额必须等于参数表"的校验。
6. **不得顺带做本轮之外的事**（禁区清单）：
   - ❌ 不做 M4 上云 / 多用户 / 认证（用户 2026-09-29 确认"单独规划，不进本轮"）
   - ❌ 不改 13 个属性维度的名称、数量、别名（M3 只加 `parent_id` 层级，不改既有维度语义）
   - ❌ 不发属性点作为成就奖励（成就只发金币 + 徽章）
   - ❌ 不做"万能豁免券"（必须指定日期 + 时段）
   - ❌ 不动 E 类未启动项（B1 拍照识别 / C1 日记追问联动 / D3 AI 分析显化）——想法未问清
   - ❌ 挑战金币上调后，**不得**为"平衡"而擅自下调商店定价（两处都必须由 AI 依行情快照自主定价）

## 一、决策表

### P0 · 新 3 条实测反馈 + 1 个真 bug

#### N1 · 挑战奖励改由 AI 主导定价（推翻旧铁律）

| # | 决策 | 结论 |
|---|---|---|
| N1-1 | 谁定金额 | **AI 直接给出每个档位的金币奖励**（`coin_reward` 整数字段），不再由 `COIN_TABLE` 派生 |
| N1-2 | 押金 | **由系统按固定比例派生**：`deposit = max(1, round(coin_reward * 0.6))`。AI **只给奖励、不给押金**（用户选择"b"：押金要够痛但可承受，比例稳定比放开更符合设计意图） |
| N1-3 | 上限 | **不设经济上限**（用户原话："绝对上限 AI 自己判断不出来吗？"）。只保留**解析兜底**：非整数 / ≤0 / 缺失 → 回落 `COIN_TABLE` 的对应档位值 |
| N1-4 | 给 AI 的参照 | **只给"行情快照"，不给逐件商品清单**（用户明确："奖励和商店不能太挂钩，那不然我都不能攒金币换奖励了"）。快照内容见 N1-5 |
| N1-5 | 行情快照构成 | ① 当前金币余额 ② 近 7 天收入 / 支出合计 ③ 日常赚币规则（记录事件 +2/条、连续写日记 7 天 +30）④ 商店价位**区间**（最便宜 ~ 最贵，如"20 ~ 90 币"）。**不含**任何单件商品名称与价格 |
| N1-6 | 内部一致性硬要求 | prompt 必须写明：① 同一批候选中**难度越高奖励必须越多**；② 同一挑战的多档之间**奖励必须随 difficulty 递增**；③ 奖励必须**显著高于"记一笔事件"的量级**（挑战是主要收入来源） |
| N1-7 | 连带修复（必须同批做） | `app/prompts/shop.py` 的 `build_pricing_messages` 也**注入同一套行情快照**。否则挑战奖励上调后"最贵 90 币的电影"会显得极便宜，**两套经济脱节** |
| N1-8 | 商店侧的真实缺口（本批一并修） | `SHOP_SYSTEM_PROMPT` 要求 AI"结合他近期的**金币获取速度**折算成约几天的努力"，示例甚至写死"日均约 5 币"——但 `build_pricing_messages()` **从未传入任何收入数据**，AI 只能凭空编造。**本批必须补上收入与余额输入** |

> **为什么"行情快照"能防通胀**：AI 的失控根源不是"不可信"，而是**看不到全貌**（不知道 90 币是大钱）。事前给锚 → AI 仍是唯一决策者；事后夹取 → 本质是不信任，且 AI 学不到。用户选"给锚"与"信赖 AI"的理念一致。

#### N2 · 周挑战形态（限制"每日重复型"占比）

| # | 决策 | 结论 |
|---|---|---|
| N2-1 | 根因 | `app/prompts/challenge.py` 的 `build_challenge_messages` 里，weekly 只有一句「周挑战（本周内完成）」，**没有告诉 AI 周挑战应是"独立大任务"** → AI 自然按"连续 N 天"切档 |

| N2-4 | 落地规则 | prompt 明确：周挑战 = **一件有分量的独立任务，一周内自行安排时间完成**；候选中**独立型应占多数**（weekly 候选 2 个 → **最多 1 个**是"连续 N 天"型）。日挑战保持"每日小习惯"定位不变 |

#### N3 · 搜索范围去掉 AI 内容

> 这三项的用户想法**已在 2026-09-28 访谈中问清**（见 `DECISIONS.md`「v1.10 已登记待办」），本轮按此落地，不重问。

#### M1 · 成就系统（对应 `GAMIFICATION_MODULES.achievements`）

| # | 决策 | 结论 |

#### M2 · 豁免券（时段券，AI 判动机浮动）

| # | 决策 | 结论 |
|---|---|---|
| M2-1 | 形态 | **时段券**：购买时**必须指定日期 + 时段**（如"今天下午""周六全天"），只在该时段生效、过期作废 |
| M2-2 | 效果 | 该时段内**目标未完成不扣分或减少扣分**；时段内做的**其他事情照常加别的维度点数** |
| M2-3 | 代价 | **AI 判动机后浮动**——用户可写一句理由；AI 判为**正当紧急** → 正常价；判为**明显逃避/拖延** → **提价**或**额外扣少量属性点**（如规划力），并**把理由展示给用户** |
| M2-4 | 用户原话精神 | "要是买来随便一个时间都可以，感觉临时不想干活用券，感觉很奇怪，不利于自身成长"——**绝不能做成万能券** |
| M2-5 | 联动 | 判定链路需查询"该时段是否有券"（改动面涉及 `judge_service` 与时段匹配） |

#### M3 · 属性满 100 拆分子维度

| # | 决策 | 结论 |
|---|---|---|
| M3-1 | 触发 | 某主维度接近/达到 100 时，**AI 结合用户实际记录提议 2~4 个细分方向**（用户举例：智力 → 数学思维 / 空间想象 / 逻辑推理），**用户确认后才解锁** |
| M3-2 | 数值 | 子维度**独立累积**（各自 0~100）；主维度满 100 后**保持不变** |
| M3-3 | 代价 | 维度从平面变**层级**（`attributes` 加 `parent_id`）；判定时要决定行为落在主维度还是子维度 |
| M3-4 | 与 V1 的关系 | 属性面板需相应改版 → **建议 P1-3 与 P2-2（可视化）连做**，或至少 V1 的量程改造要预留层级显示空间 |
| M3-5 | 风险提示 | 本项**改判定链路语义**（行为该落主维度还是子维度），是 P1 里风险最高的一项 → **建议放 P1 最后做**，且必须在副本库上充分验证 |

### P2 · 页面结构合并（U1/U2/U3）

#### 现状（真实取证）

`App.vue` 当前 **11 个 tab**：
`属性面板` · `今日盘点` · `记录事件` · `手账本` · `判定中心` · `目标` · `挑战` · `锚点库` · `角色档案` · `纯享记录` · `设置`

| # | 决策 | 结论 |
|---|---|---|
| U1-1 | 目标形态 | **三页合并为一个统一入口「今日盘点」**：原「今日盘点」+「记录事件」+「目标」 |
| U1-2 | 合并后结构 | **按性质分区块**（保留现有结构）：【规划内】→【可选】→【负面】→【其他】→【自由记一笔】→【今日已记】 |
| U1-3 | 【规划内】内容 | **目标任务 + `planned` 性质的打卡项目**统一在此区块显示（这正是用户说的"目标定好之后会在今日盘点的规划内出现"——与现有 `nature='planned'` 是同一个词、同一个概念） |
| U1-4 | 【自由记一笔】 | 原「记录事件」的输入区：**用户自己随便想到的事件在这里记**（用户原话） |
| U1-5 | 职责划分 | 「今日盘点」= **每日要被提醒回顾的**（结构性、规划内）；「自由记一笔」= **临时想到的**。两者在**同一页**，消除"不知道一件事该去哪个页面记"的困惑 |
| U2-1 | 迁入 | 打卡项目管理（现挂 `SettingsView.vue` L351-352 的 `<ItemManager />`）**迁到「今日盘点」页**，不再放设置里 |
| U2-2 | 形态 | **页内可折叠面板**（用户选择项 1）——日常不占地方，需要时展开 |
| U3-1 | 目标与打卡项目的关系 | **呈现层合并，数据模型不动**（用户确认）。今日盘点里不再区分"这是目标还是打卡项"，统一成「规划内」清单；管理面板里两块并排 |
| U3-2 | 为什么不动模型 | 两者语义差异大（目标有 `deadline`/`reward`/`penalty`；打卡项目有 `frequency_type`/`nature`）；真合并需迁移 4 条 `checkin_items` + 31 条事件的 `item_id` 引用，代价与收益不成比例 |
| U3-3 | 关键发现（已核实） | **机制其实已经通了**：`checkin_items.goal_id` 早就能把打卡项目挂到目标下，`GoalsView` 已渲染 `g.progress`（v1.7 C3）。**缺的只是入口在「设置」页、"给目标加日常任务"的按钮不在目标上下文里** |
| U3-4 | tab 变化 | **11 → 9**：移除 `event`（记录事件）、`goals`（目标）；**「纯享记录」保留**（写日记、不加点，用户确认"日记的地方是保留的"） |

**合并后的 nav**：
```
属性面板 · 今日盘点 · 手账本 · 判定中心 · 挑战 · 锚点库 · 角色档案 · 纯享记录 · 设置
```

#### 目标 / 打卡项目的创建与管理放哪

| 内容 | 位置 |
|---|---|
| 目标的创建、达成、失败、取消 | 「今日盘点」页内的【规划设置】折叠面板 → **目标**分区 |
| 打卡项目的增删改停用 | 同一个【规划设置】面板 → **打卡项目**分区（两块并排） |
| 给目标挂日常任务 | 同上：新建打卡项目时选所属目标（复用现有 `goal_id` 字段） |
| 目标进度展示 | 今日盘点【规划内】区块内联展示（沿用 `goal_service` 的 `progress` 口径，**不自动达成**） |

> **注意**：v1.7 决策 7 明确"进度只做展示、不自动达成，达成仍由用户手动点"。**本轮保持该决策**。

### P2 · 可视化重做（V1/V2/V3）

#### V1 · 雷达图

| # | 决策 | 结论 |
|---|---|---|
| V1-1 | 现状 | `AttributePanel.renderRadar()`：`indicator.max = 100` 固定量程、`radius='65%'`。属性值实际集中在 **50~73** → 在 0~100 量程下多边形近乎居中圆形，**形状无信息量**；13 个轴名在外圈互相挤压 |
| V1-2 | 用户选择 | **改量程 + 修排版**（保留雷达图）。用户原问："排版和量程改完有用好看吗？不然要么去掉？" → 结论：**量程改造是雷达图存在的唯一理由**（因为页面上已有 13 条水平属性条表达精确值，雷达图与它信息重复，其不可替代价值只剩"一眼看形状"） |
| V1-3 | 量程改法 | 由固定 `max:100` 改为**按当前实际值区间动态缩放**（如 `[floor(min)-5, ceil(max)+5]`，下限不低于 0）；轴标签或 tooltip **同时标注真实值**，避免"动态量程导致绝对水平失真"的误读 |
| V1-4 | 排版改法 | 轴名错开 / 缩小字号 / 必要时缩短显示名（**不得改维度本名**，只改显示）；半径与容器高度重新配比 |

#### V3 · 活动热力图

| # | 决策 | 结论 |
|---|---|---|

## 二、批次划分与交付顺序

```
批次 P0（经济定价重构 + 搜索收敛 + label 修复）    N1 + N2 + N3 + N4
   P0-1  后端：挑战奖励改由 AI 主导定价（含行情快照 + 商店锚注入）
   P0-2  后端：周挑战形态改为"独立大任务为主"
   P0-3  前端：搜索去掉 AI 内容 + 修复 label 截断

批次 P1（已登记三项玩法）                          M1 + M2 + M3
   P1-1  成就系统
   P1-2  豁免券（时段券）
   P1-3  属性满 100 拆分子维度   ← 风险最高，放最后

批次 P2（结构与可视化）                            U1~U3 + V1~V3

**顺序理由**：
- **P0 最优先**——它改的是"钱"，而 P1 的成就/豁免券都**依赖金币经济**。经济口径不定，后面两项的定价会白做。
- **P1-3 放批次最后**——它动**判定链路语义**（行为落主维度还是子维度），是全轮风险最高项。
- **P2-2 与 P1-3 有耦合**（M3-4：层级化后属性面板要改版）→ 若 P1-3 先做完，P2-2 的 V1 改造要一次性考虑层级显示；**实现者可在 P1-3 完成后再动 V1**，避免返工两次。
- **P2-1 独立性强**（纯前端信息架构），但改动面广（11 → 9 个 tab）→ 放在最后，便于前面几批稳定后一次性重排。

def snapshot(db: Session, user: User) -> str:
    """构建"行情快照"文本（供挑战定价与商店定价共用）。

**输出示例**（供实现者对齐格式）：

```
【金币余额】40 币
【近 7 天收支】收入 +12 币，支出 -10 币
【日常赚币】记录事件 +2 币/条；连续写日记 7 天 +30 币

#### P0-1-2 · prompt 契约（`app/prompts/challenge.py`）

**输出格式扩展**——每个 challenge 与每个 variant 都带 `coin_reward`：

```json
{
  "title": "整理一份今日任务清单",
  "description": "（默认档要求）",
  "difficulty": 3,
  "coin_reward": 35,
  "related_attributes": ["规划力"],
  "variants": [
    {"label": "3 项", "description": "...", "difficulty": 2, "coin_reward": 20},
    {"label": "5 项", "description": "...", "difficulty": 3, "coin_reward": 35},
    {"label": "10 项", "description": "...", "difficulty": 5, "coin_reward": 70}
  ],
  "reason": "为什么给你这个挑战"
}
```

**新增 rules（追加到「硬性要求」）**：

- `coin_reward` 是**你为这个挑战判定的金币奖励**，必须是**正整数**。
- **判断依据**（必须综合，不得只看难度数字）：
  - 任务本身的**分量与代价**（耗时、心理门槛、是否需要他人配合）
  - 用户当前**余额与近期收入水平**（见 user 消息中的行情快照）——他缺钱时给得实在些，余额充裕时不必虚高
  - **要让挑战成为他的主要收入来源**：奖励应显著高于"随手记一笔事件"（+2 币）的量级
- **同一批候选中，难度越高奖励必须越多**；**同一挑战的多档之间，奖励必须随 difficulty 递增**（不允许出现"难度 5 给 10 币、难度 2 给 50 币"）。
- **不要给押金**（系统按奖励比例派生）。
- **不要给整齐划一的档差**（不要机械"每档 +5"）——按任务实际分量的差异给（简单任务档差可小、困难任务档差应大）。

> ⚠️ **实现者注意**：`COIN_TABLE` 的值**不要**写进 prompt。它的作用只剩"解析兜底"，写进去会把 AI 拽回参数表，违背 N1-1。

1. 副本库上构造"连续写日记 7 天" → 解锁 `journal_streak_7`，`coin_ledger` 新增一条 `source='achievement'`；**再次触发不重复发放**（幂等）
2. `Σ coin_ledger.delta == user_profiles.coins` 仍成立

4. **不发属性点**（`attribute_history` 无任何新增行来自成就）
5. 真实库老数据：`events` 31 / `ai_judgments` 31 / `attribute_history` 122 / `coin_ledger` 2 / `coins` 40 **全部不变**（本轮不追溯补发任何成就）

### P1-2 · 豁免券（M2）

#### 数据模型（新表）

```python
class Exemption(Base):
    """豁免券（v1.10）：时段券——只对指定日期 + 时段生效，过期作废。

    **不是万能券**（用户明确要求）：target_date + period 必填。
    """
    __tablename__ = "exemptions"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), nullable=False)
    target_date: Mapped[str] = mapped_column(String(10), nullable=False)   # YYYY-MM-DD
    period: Mapped[str] = mapped_column(String(20), nullable=False)       # morning/afternoon/evening/allday
    reason: Mapped[str] = mapped_column(Text, default="")                 # 用户写的理由
    coin_cost: Mapped[int] = mapped_column(Integer, default=0)            # AI 判动机后的实际价格
    motive_note: Mapped[str] = mapped_column(Text, default="")            # AI 的动机判断说明（展示给用户）
    extra_penalty: Mapped[float] = mapped_column(Float, default=0.0)      # 判为逃避时的额外扣点（如 0.5）
    status: Mapped[str] = mapped_column(String(20), default="active")     # active/used/expired
    created_at: Mapped[datetime] = mapped_column(DateTime, default=_now)
```

#### 定价与动机判定（新 prompt `app/prompts/exemption.py`）

- 输入：目标日期/时段、用户理由、近期记录、属性状态、**行情快照**（复用 `economy_service.snapshot`）
- 输出：

```json
{
  "coin_cost": 30,
  "motive": "legitimate",
  "motive_note": "展示给用户的判断说明",
  "extra_penalty": 0
}
```

- `motive` ∈ `legitimate`（正当紧急）/ `evasive`（明显逃避）
  - `legitimate` → 正常价、`extra_penalty = 0`
  - `evasive` → **提价**（如基准价的 1.5~2 倍）或 `extra_penalty` 给 0.3~0.5，**二者至少取其一**，并在 `motive_note` 明说
- **`motive_note` 必须给出实质判断**，不得写成中性废话（同商店 `worth_note` 的标准）

#### 生效链路（`app/services/judge_service.py`）

**这是本项的核心改动，需谨慎**：

- 判定时查询：**该事件 `occurred_at` 所属的日期 + 时段**是否存在 `status='active'` 的券
- 命中时：
  - 该时段内**目标类**的未完成 / 退缩 → **不扣分或按比例减少扣分**
  - **其他维度照常加点**（不得整条事件跳过判定）
- 券在**使用后置 `used`**；过了 `target_date` 未使用 → 惰性置 `expired`（参考 `challenge_service.expire_stale` 的做法）

> ⚠️ **判定链路的改动风险高**（v1.5 起"重判就地更新"的契约、v1.6 的增量修订契约都在这条链路上）。**实现者必须先完整读一遍 `judge_service` 的现有分支**，再动手；且**只在"是否需要扣分"的判断处插入一次查询**，不要重构既有结构。

#### 购买

- 走 `coin_service.grant(source=...)` 扣币。**`SOURCES` 需新增 `'exemption_purchase'`**（当前元组里没有该值）
- 余额不足 → 拒绝（复用 `InsufficientCoins`）

#### 验收标准

1. 购买指定"今天下午"的券 → `coin_ledger` 扣币一条、`exemptions` 一行 `status='active'`
2. 在该时段记一件**负面/退缩**事件 → 判定**不扣或减扣**（附 `final_changes` 对照）；**同时段另一件正面事件照常加点**
3. 在**非该时段**记同类事件 → **照常扣分**（证明确实按时段生效）
4. AI 判为 `evasive` → `coin_cost` 提高或 `extra_penalty > 0`，且 `motive_note` 有实质说明（附 AI 返回）
5. **万能券不可能**：不指定日期或时段的请求 → 400
6. 过了 `target_date` → `status` 变 `expired`，不再生效
7. **重判链路不受影响**：对已判定事件做一次重判 → 仍"就地更新、id 不变、审计只增不删"
8. `Σ coin_ledger.delta == user_profiles.coins`

### P1-3 · 属性满 100 拆分子维度（M3）

> **本轮风险最高项**。建议在 P0 / P1-1 / P1-2 全部稳定后再动；且必须与 P2-2 的 V1 协调（见 M3-4）。

#### 数据模型

`Attribute` 新增：

```python
# v1.10：父维度（层级）。NULL = 主维度；非空 = 某主维度的子维度。
parent_id: Mapped[int | None] = mapped_column(ForeignKey("attributes.id"), nullable=True)
```

- 走 `migrate_schema` 自动加列
- **既有 13 维 `parent_id` 全为 NULL**（主维度），行为不变

#### 触发与确认

- 触发条件：某主维度 `current_value >= 100`（或接近，阈值由实现者定并写明）
- AI 结合**该维度的历史记录**提议 2~4 个细分方向（复用 `judge_service` 的上下文构建）
- **必须用户确认后才创建子维度**（不自动加）

#### 判定链路改动

- 判定时需决定行为落在**主维度还是子维度**：
  - 主维度未满 100 → 所有加点仍落**主维度**（行为不变）
  - 主维度已满 100 → 加点落**匹配的子维度**（由 AI 在 `affected_attributes` 里给出子维度名）
- **`_clamp_attribute_value` 统一封顶**（主/子一致，0~100）
- **子维度不影响主维度数值**（M3-2：主维度满 100 后保持不变）

#### 展示

- 属性面板：主维度下**缩进显示子维度**（或折叠展开）
- **与 V1 的协调**：雷达图量程改造需考虑子维度是否上雷达图——**建议子维度不上雷达图**（否则轴数暴增），只在条形列表中展开显示

#### 验收标准

1. 副本库上把某维度推到 100 → 触发 AI 提议 → 用户确认 → 创建子维度且 `parent_id` 正确
2. 之后该维度的行为加点**落在子维度**、主维度保持 100（附 `attribute_history` 证据）
3. 未满 100 的维度**行为完全不变**（回归测试）
4. 未确认时**不创建**任何子维度
5. 真实库 13 维 `parent_id` 全为 NULL，`attribute_history` 122 条不变、账目仍自洽
