## 〇、本轮定位与总原则

**这是一次「事件录入口」的体系性重构**，不是加功能。核心理由：现有事件表单的三件套（事件类型下拉 + 时长/距离/强度）是为运动场景设计的，用户实际记录的学习、作息、情绪、饮食、杂项全都套不进去，导致录入成本高、分类卡壳、数据失真。

**三条不可违背的总原则**：

1. **数据红线（最高优先级）**：用户本地 `game_of_life.db` 存有真实生活记录，**禁止任何物理删除**（判定、审计、事件一律只归档不删除）；新增表由 `create_all` 创建，`events` / `goals` 等既有表加列必须走 `app/database.py::migrate_schema` 的启动自动迁移；**老数据必须全部可读、可正常展示、可正常判定**，不得出现报错或空白。
2. **兼容过渡**：`event_type` 字段**保留在数据库不改不删**（历史数据依赖它），仅在前端隐藏、新建事件写默认值；`params`、`content`、`source` 等字段语义保持向后兼容（详见批次 A 的字段契约）。
3. **一批一 commit，中文 message**，格式 `类型: 简述`（feat/fix/refactor/docs/chore/test）；只 commit，**不 merge、不 push**；严禁提交 `.env`、`*.db`、`__pycache__/`、`node_modules/`、`.workbuddy/`。

**本轮禁区（一个都不要碰）**：

- 饮食拍照识别（`docs/DECISIONS.md` → Backlog B1，需新增上传能力 + 视觉模型，下批）
- 日记追问提示与打卡补充的跨模块联动收回（Backlog C1，下批）
- 定时提醒/系统通知（用户 2026-09-22 明确本轮不做）
- AI 分析过程流式显化（Backlog D3，待定）
- 低置信度提示"只提醒一次"（Backlog ②，用户口径未定，勿擅自实现）
- 首页问候卡片、语音输入、桌宠、金币商店、排行榜（均未定）

## 三、批次 A · 后端

### A1 · 打卡项目数据模型（新建表 `checkin_items`）

**现状**（`app/models/__init__.py`）：`Event`（L110 起）用 `event_type`（positive/negative/goal 三值）+ `category`（自由字符串）+ `params`（JSON）+ `content` 承载全部信息，无"项目"概念。

**要做**：新增 ORM 模型 `CheckinItem`，表名 `checkin_items`。字段设计：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | Integer PK | 自增 |
| `user_id` | ForeignKey("users.id") | 多用户预留，与现有表一致 |
| `name` | String(100) | 项目名，如"晨跑""背单词""久坐" |
| `nature` | String(20) | `planned` / `optional` / `negative` / `other`，默认 `other` |
| `frequency_type` | String(20) | `daily` / `weekly` / `none`，默认 `none` |
| `frequency_target` | Integer | `weekly` 时的每周目标次数（如 3）；`daily`/`none` 忽略 |
| `category` | String(50) | 项目所属生活面（学习/运动/作息/社交/饮食/情绪/其他），供判定注入用 |
| `related_attribute` | String(50) | 可选，主要影响的属性维度（复用现有 13 维常量 `app/constants.py::ATTRIBUTE_DIMENSIONS`） |
| `goal_id` | ForeignKey("goals.id") nullable | 关联目标（可选，为空表示不挂目标） |
| `enabled` | Boolean | 是否在用（停用不删除，保留历史记录的引用） |
| `sort_order` | Integer | 手工排序用，默认 0 |
| `created_at` / `updated_at` | DateTime | 与其他表一致 |

**同时**：`Event` 表新增可空外键列 `item_id`（`ForeignKey("checkin_items.id")`，nullable）——记录"这条打卡属于哪个项目"。**老事件 `item_id` 为 NULL，属正常，所有下游逻辑必须容忍 NULL**。该列由 `migrate_schema` 自动添加（可空，符合现有迁移约束）。

**同步交付**：
- `sql/schema.sql` 补 `checkin_items` 建表语句 + `events.item_id` 列（保持与 ORM 一致，供 MySQL 迁移参考）
- `app/routers/items.py` 新路由，挂到 `app/main.py` 的 `/api` 前缀下：
  - `GET /api/items` — 列表（可按 `enabled` / `nature` 过滤）
  - `POST /api/items` — 新建
  - `PUT /api/items/{id}` — 修改（含启用/停用）
  - `DELETE /api/items/{id}` — **停用（`enabled=False`），不物理删除**（历史事件引用它）
  - `GET /api/items/stats` — 各项目频率达成情况（`{item_id, name, nature, frequency_type, frequency_target, this_period_count, samples: [首次打卡日, 日期2, ...]}`，"本期"= daily 取今天、weekly 取本周一至今、none 不算达成率）
- `app/schemas/__init__.py` 增 `CheckinItemIn` / `CheckinItemOut`

**验收标准**：
1. 启动服务后 `checkin_items` 表自动创建，`events` 表新增 `item_id` 列（迁移日志打印 `[migrate] 已添加缺失列 events.item_id`），**老数据 14+ 条判定记录全部可正常打开**
2. 建项目 → 查列表 → 停用 → 列表 `enabled=false` 但仍可查到，且历史事件仍能读到该项目的名称
3. `GET /api/items/stats` 对 `weekly`+`target=3` 的项目，本周打了 1 次卡时返回 `this_period_count=1`（对应"本周运动 1/3"提示）

### A2 · 事件录入接口适配

**要改**（`app/schemas/__init__.py` → `EventCreate`；`app/routers/events.py` → `create_event`）：

1. **新增可选入参** `item_id: int | None`，以及 `occurred_at` 沿用现有字段（补记时写实际发生时间）
2. **表单通道（source=form）不再要求 `event_type`**：删掉 `events.py` L52-56 的「结构化打卡必须指定事件类型」400 报错分支。改为：
   - 传了 `item_id` → 从项目**派生**：`category = item.category`、`event_type` 按性质映射（`negative` → `"negative"`，其余 → `"positive"`）、`title = 内容首行(≤40字) or item.name`
   - 未传 `item_id`（纯自由记一笔）→ `event_type="positive"`、`category` 取传入值或 `"其他"`
3. **内容化**：表单通道也接受 `content`（正文），与 `params` 并存。**字段契约**：`content` = 用户手写的正文（必填可空）；`params` = 可选数字键值对（如 `{"时长(分钟)": "30", "距离(公里)": "5"}`），**键名由前端自由传、不校验白名单**；`params` 中 `_` 开头的键仍是系统内部保留（现有 `judge_service.format_event_description` L148-151 已跳过，勿破坏）
4. `is_pure` 纯享记录逻辑保持不变

**验收标准**：
1. `POST /api/events` 带 `{item_id, content, params}` 成功；不带 `item_id` 仅带 `content` 也成功（不再 400）
2. 用 `item_id` 指向一个 `nature=negative` 的项目建事件，落库 `event_type="negative"`
3. 现有前端（尚未改造时）仍能正常提交（向后兼容，`event_type` 传了就用传的）

### A3 · 判定链路适配（判定输入与合并）

**要改**（`app/services/judge_service.py`、`app/prompts/judge.py`）：

**A3-1 · 事件描述注入项目上下文**
`format_event_description`（L138）在现有 "事件类型/类别/简述" 基础上，**新增**（有则加，无则跳过）：
```
打卡项目：晨跑（规划内 · 每天 · 运动）
项目频率：本周已完成 2/3 次
```
数据从 `event.item_id` 关联查 `CheckinItem`；`item_id` 为 NULL 时**整块不输出**（兼容全部老数据）。

**A3-2 · 可选类加分规则写入 prompt**
在 `JUDGE_SYSTEM_PROMPT` 新增一节「打卡项目性质与加点」：
- `planned`（规划内）：完成 → 正常判定；**未完成不单独扣分**（频率未达标已在页面如实提示，扣分只在 AI 认定"明显懈怠/长期落空"时给规划力减分，并须在加权推导中说明依据）
- `optional`（可选）：**默认不是"做了就加分"**——先看事件内容：若同类 `planned` 项目本周期已完成（系统会注入项目频率数据）且本条是**额外、主动、有实际投入**的（如规划内学习已完成又额外学了一门课），可给 `规划力` / 相关能力维度小幅加分；若只是随手消遣性质，**不加分或仅情感维度小幅加分（幸福感/意义感）**；一律须在加权推导中说明判断理由
- `negative`（负面）：**每次出现都正常减分，绝不去重**（延续 v1.2 已有规则）
- `other`（其他/杂项）：按内容常规判定，不加不减性质权

**A3-3 · 跨来源合并（决策 8）**
现状已有 `_today_events_context`（L107，注入当天已记录事件）与 prompt 的「事件去重」节（L29-35），但**规则是"倾向于去重、跳过"**，且不提"合并"概念、也不返回明细。

改法：
1. **prompt 规则改写**：把「不确定时倾向正常判定（而不是倾向去重）」改为——识别到与当天/近期记录是**同一件事**时，**合并处理**：正面事实分只计一次（取影响更深的口径），新增的**感受/反思/意义**部分照常加分；并在输出中**列出合并明细**。
2. **新增输出字段** `merged_with`：数组，元素形如 `{"ref": "同日打卡记录#123 晨跑", "note": "同一件事，事实分不重复计；本条补充的成就感另计"}`。无合并时返回 `[]`。
3. **服务层落库**：`ai_judgments` 表新增 `merged_with` JSON 列（`migrate_schema` 自动迁移，可空安全）；`judge_event` / `rejudge` / `dispute` 三处落库；`GET /api/judgments`、`GET /api/judgments/{id}`、`POST /api/events/{id}/judge` 三处响应返回。
4. **跨来源识别范围**：沿用 `_today_events_context` 的"当天"范围（含 form 与 journal 两类来源），并额外注入**近 24 小时内**的同标题/同类别事件（复用 `_recent_events_context` 已有能力，必要时把窗口从 7 天收窄补充说明"仅用于判断是否同一件事，不得用于其他判断"）。**注意**：注入文本必须标注这是"供判断是否同一件事"，避免 AI 误把它当成"要一起判定的内容"。

**验收标准（必须真实调用 DeepSeek 验证并给出证据）**：
1. **合并**：先在打卡记录"晨跑 5 公里"（关联 `planned` 项目），再提交日记提到"早上跑了 5 公里，跑完很有成就感" → 判定卡 `merged_with` **非空**，体能类事实分未翻倍（与只记打卡时的加点量级相当），且幸福感/意义感等情感维度有加分；判定卡前端能显示"已与 1 条记录合并"
2. **不误合并**：同一天"晨跑 3 公里"与"晚上又跑了 5 公里"两条**互不合并**（各自正常判定）
3. **可选类**：某 `optional` 项目在本周 `planned` 同类已完成的情况下提交"额外学了一门课"，判定含 `规划力` 正向加点且加权推导中说明"规划内已完成、此为额外投入"；随手看了个娱乐视频的 `optional` 记录**不出现**规划力加分
4. **负面不去重**：同一天连续记两次"久坐 3 小时" → **两次都减健康分**
5. **老数据兼容**：`item_id` 为 NULL 的历史事件重新触发判定不报错、项目上下文块不出现

### A4 · 目标进度来源（决策 7）

**要改**（`app/services/goal_service.py`、`app/routers/goals.py`）：

1. `goals` 表**不加列**（`CheckinItem.goal_id` 已表达关联关系），改为**查询时计算**：目标进度 = 关联打卡项目在本周期的完成次数 / 目标次数（或按项目 `frequency_target` 汇总）
2. `GET /api/goals` 响应新增 `progress`：`[{"item_id": 1, "name": "背单词", "this_period_count": 2, "target": 3, "rate": 0.67}]` + 汇总 `progress_rate`（各项目达成率的平均，无关联项目则为 null）
3. **明确不改**：`achieve_goal` / `fail_goal` 的手动结算逻辑（奖励/扣分）保持原样，**不自动达成**——进度只做展示，达成仍由用户点"达成"（避免系统替用户拍板）

**验收标准**：给一个目标挂 2 个打卡项目，其中 1 个本周达标、1 个未达标 → `GET /api/goals` 返回两条 progress 各自正确、汇总 rate 为其均值；未挂项目的目标 `progress` 为空数组且 `progress_rate=null`（前端不展示进度块）。

## 四、批次 B · 前端

### B1 · 录入表单重构（`frontend/src/components/EventForm.vue`）

**现状**：模式切换「结构化打卡 / 自由日记」；打卡表单为「事件类型下拉 + 类别下拉 + 简述 + 时长/距离/强度 + 补充说明」（L235-280）。

**改成**：

```
[ 打卡 ]  [ 自由日记 ]                        ← 保留双通道

打卡模式：
  打卡项目  [下拉：我的项目，按性质分组显示｜+ 新建项目]
  写点什么  [textarea 多行，占位："今天做了哪些运动？现在感觉怎么样？"]   ← 必填（空则提示）
  关键数字（可选）  [可增删的「名称 + 数值」行，默认空；一行示例占位"时长(分钟) = 30"]
  实际发生时间（可选）[datetime-local，默认现在；补记时改]
  [ ] 纯享记录（只记录，不做 AI 分析、不加点）

自由日记模式：保持现状（一段 textarea）+ 现有草稿缓存
```

**改动要点**：
- **删掉**：事件类型下拉、类别下拉、时长/距离/强度三个固定框
- **新增**：项目下拉（数据源 `GET /api/items?enabled=true`，按 `planned/optional/negative/other` 分 optgroup）、正文 textarea、键值对编辑器（支持 0~5 行，行可增删）、实际发生时间
- **提交载荷**：`{item_id, source: 'form', content, params: {键: 值}, occurred_at}`；自由日记保持 `{source:'journal', content}`
- **保留**：现有 localStorage 草稿缓存、`result` sessionStorage 持久化、追问卡交互、`去判定中心确认` 按钮（这些是 v1.3/v1.5/v1.6 成果，**不得破坏**）
- 老事件编辑（`EventUpdate` 回填）：`item_id` 为 NULL 的老事件，项目下拉显示"（无项目，历史记录）"，允许改选或保持为空——**不允许因老数据缺少 item 而阻止保存**

**验收标准**：
1. 建了 4 类各一个项目后，下拉按四组正确分组显示
2. 选项目 + 写正文 + 加一行"时长(分钟)=30" → 提交成功且落库 `params={"时长(分钟)":"30"}`、`content` 为正文
3. 未选项目直接写正文也能提交成功
4. 切页返回、刷新后草稿都在（localStorage），提交后判定结果卡仍会持久化（sessionStorage）
5. 打开一条 `item_id` 为空的老事件编辑 → 能正常保存，不报错

### B2 · 打卡项目管理页（新增 `frontend/src/components/ItemManager.vue`）

- 位置：作为「设置」页的一个新分区（或独立 tab，二选一，建议设置页分区，减少一级导航）
- 能力：列表（按性质分组，显示名称/性质/频率/关联属性/启用状态）、新建、编辑、停用/启用；**不提供物理删除**（按钮文案写"停用"）
- 频率编辑：`daily` / `weekly`（填目标次数）/ `none`；可选关联目标（下拉现有 goals）
- 提示文案：新建时对四类性质给一句话说明（如"负面：久坐、熬夜这类，记一次扣一次分"），**不预置任何示例项目**（用户自建）

**验收标准**：新建 4 类项目各一 → 列表分组正确 → 编辑改频率生效 → 停用后录入页下拉不再出现（但历史记录仍能显示其名称）

### B3 · 今日盘点页（新增 `frontend/src/components/TodayCheckin.vue`）

- 展示当天所有 `enabled` 的 `planned` / `optional` 项目（负面项目**不强制罗列**，避免噪音；可折叠展开"负面项"供快速补记）

- 批量提交：允许一次性把多个项目的记录一起提交（逐条创建事件并各自判定，**不要合成一条事件**）

**验收标准**：当天 3 个 `planned` 项目、其中 1 个已打卡 → 页面显示三条，已打卡那条标注完成、另两条显示未达标提示；在页面上给 2 个项目各写一句话提交 → 数据库新增 2 条独立事件（`item_id` 各自正确）

### B4 · 事件列表分组收纳（决策 10）

**范围**：记录事件那个页面的列表（`EventForm` 同页的列表区，或 `TimelineView` 中的事件栏，以当前承载事件列表的组件为准）

  - 事件：默认整个事件栏**只占一行**（显示"事件 3 条"），点击展开后列出每条（一行一条：项目名 + 摘要 + 加点概览）；再点某条才展开详情（内容 / 参数 / 判定明细）

## 五、批次 C · 提交交互修复

### C1 · 「AI 正在分析…」状态 + 防重复点击（决策 9）

**现状**：`frontend/src/components/JudgmentList.vue` 的 `runAction` 已有 `busy` 标志与按钮 `:disabled="busy"`，v1.6 已实现保留式成功反馈（绿色状态行）。但用户实测仍感到"点了没反应、想再点"——**缺的是"正在处理"这个可见状态**（`busy` 期间按钮只是变灰，没有文字变化）。

**改成**：
1. 点击提交（确认 / 补充 / 反驳）后，**按钮文案立即变为「AI 正在分析…」并显示 spinner**，全卡操作按钮禁用（含项目下拉/输入框，防中途改动）
2. 状态由 `busy` 驱动，**必须覆盖整个请求周期**（含 LLM 超时重试那 1 次，见 `llm_service.chat_json`），请求返回（成功或失败）才恢复
3. **超时保护**：请求超过 60 秒仍未返回时，提示"AI 响应较慢，可继续等待或取消"，但不自动清空状态
4. 沿用 v1.6 保留式成功反馈与 v1.4 就近错误提示（**不要回退**）

### C2 · 误点取消（决策 9）

- **输入型操作**（补充信息 / 反驳，需要先输入文本）：输入区提供「取消」按钮 —— 关闭输入区、清空输入、回到未操作态（不提交）
- **直接生效型操作**（确认入账 / 删除事件）：**不加二次确认弹窗**（确认入账有低置信度拦截兜底；删除已在 v1.5 有明确按钮语义）——如需确认，仅在删除时保留现有行为
- **处理中**：取消按钮在 `busy` 期间禁用（避免中途取消造成状态不一致；若实现"取消请求"成本高，允许只禁用）

### C3 · 目标进度展示（配合 A4）

- 目标列表每条显示进度条 + "本周 2/3" 文案（数据源 `GET /api/goals` 的 `progress`）
- 无关联项目的老目标不显示进度块（不报错、不显示 0%）

**批次 C 验收标准**：
1. 点「补充信息」提交 → 按钮立刻变「AI 正在分析…」且禁点；连续快速点 3 次只产生 1 次请求（用浏览器 Network 面板截图或后端日志证明，**附证据**）
2. 请求失败 → 按钮恢复可点、输入内容保留、就近显示错误（v1.4 行为不回退）
3. 成功 → 显示 v1.6 的保留式绿色状态行
4. 补充信息输入区点「取消」→ 输入区关闭、输入清空、判定状态不变
5. 挂了项目的目标显示进度条与次数；老目标不显示进度块
