# 今日计划与快捷完成：增量开发草案

日期：2026-10-15。基线：`ba7031e`。状态：**用户已确认核心目标及人工入账流程；下述技术安排为草案，金额/进度规则未定，尚不是整体开发计划定稿或立即部署指令**。

来源：[F25～F30 与试用反馈](USER_TEST_FEEDBACK_2026-10-11.md)、[集中确认记录](TRIAL_FEEDBACK_CONFIRMATION_2026-10-15.md)、v1.7 目标/打卡约定及当前源码。此文主动补齐已有明确需求，不等待与本模块无关的账号/导出选择。

## 1. 用户确认的行为

1. 晚间回顾移除“此刻的感觉”独立选择，直接写文字；不影响主动在原文中表达感受。
2. 保留可选生活清单。另有“今日计划”，来源必须是用户在计划/目标里主动设置的行动，不从随口日记自动安排。
3. 例如“每周一跑步”“从某日开始每隔两天跑步”，只在匹配的日子显示对应行动；目标可关联多个行动。
4. 快捷结果是“完成／部分完成／未完成”；未操作时为“待记录”，不把沉默或页面没打开判成未完成。
5. 用户已选择：保存完成情况→展示奖励和属性建议→确认入账。打勾成功是事实保存成功，不等于属性/金币已变动。
6. 部分完成根据实际投入/成果，不机械按完成按钮给满额；计划与日记中的同一行动要复用事实，避免重复计奖。
7. 有明确记录与审计关联：目标/行动定义→当次安排→实际完成事实→判定建议→属性与金币流水。不能只有 UI 勾选没有持久记录。
8. 用户最新明确：点“未完成”不弹补充页面、不弹成功 toast，不重复显示“不自动扣分”说明；在原卡片确认结果后锁定，不再直接切换为完成。创建计划去掉“行动领域”。周一的安排不顺延堆到周二“今天”里，总计划列表保留定义并显示总数。

## 2. 当前已有与缺口

| 位置 | 当前能力 | 本次缺口 |
| --- | --- | --- |
| `CheckinItem`/items schema/router | daily、weekly、none，weekly 存目标次数，可关联 Goal | 指定星期、间隔天数与开始日、日程版本 |
| `TodayCheckin.vue` | 展示项目、周期次数、文字提交，关联独立事件 | 当天到期行动卡及三种完成结果；从主“今天”入口及时可见 |
| `item_service.py` | 统计关联 Event 个数，目标子进度 | 部分/未完成不能继续一条 Event 就算完整完成；补录日期与周期统一 |
| Event/AnalysisJob/AIJudgment | 原文先存、任务分析、用户确认、回执/版本 | 当次计划的身份、事实关联和完成声明需进入既有链路 |
| 属性/金币/审计服务 | 已有原子确认、实际流水、旧经济规则 | 每个安排/同一事实最多结算一次；主线分档尚无最终金额 |

这不是从零另做一套打卡账本。应复用当前认证、隔离、事件、任务与事务协议，新增必要的日程/当次状态，不平行维护另一套奖励函数。

## 3. 日程与身份方案

以下是可评审的技术方案，不要求现在在真实数据库中生成任何安排。

- 行动定义保留原项目 ID、所属用户、关联目标、启用与版本；加日程类型/参数和生效开始日。新建表单不要求“行动领域”，不能把它换名后继续要求用户选一种能力；属性建议根据实际行动判断，可涉及多个维度。兼容旧内部字段，不据此删除历史数据。
- 每天、指定星期、每隔 N 天分别建明确语义。指定星期按用户本地星期；间隔按“本地日期差 % N”，锚定开始日，不以本次点击日为新起点，也不用 24 小时毫秒跨度替代日历日。
- 既有 weekly 表示“本周 N 次”的弹性任务，**不迁成周一/三/五**；其展示为本周目标/剩余次数，具体日程由用户另设。none 仍不虚构每天必须完成。
- 当次安排以本人、行动、计划本地日期及必要序号唯一；同日多次行动若支持需明确序号，不能复用同一个完成键同时奖励两次。
- 保存计划日期、日程/目标版本、当时规则快照；后续改周期或主线不改已经产生的历史事实/结算。停用影响未来提醒，历史仍能读。
- 没有行动/周期的长期目标不擅自生成每日动作；应提供“为目标安排具体行动”入口。目标截止提醒是另一种展示，不因截止当日没打卡自动失败或扣分。
- 指定周一的任务仅在周一当天列表出现；周二不出现上一期未完成/待记录任务，也不自动把它改期。总计划列表保留启用、停用的定义，显示计划总数，可另看当次历史。新的下周一是新一期。

主“今天”查询可以只读计算应出现行动；不能用 GET 顺便造事件、发金币、触发模型或自动结算。新日程结构用新 Alembic revision，不改已执行旧迁移。

## 4. 状态与事实保存

```text
待记录
  ├─ 完成 ──────┐
  ├─ 部分完成 ──┴─ 保存声明/实际内容 → 分析建议 → 用户确认 → 已入账
  └─ 未完成 ────── 卡片内待确认 → 确认未完成 → 结果锁定（不入账）
```

状态至少分三层，不能复用一个字符串混写：

- 计划结果：待记录/完成/部分完成/未完成；是否进行中另有显示需要时再设，不把它当部分完成。
- 分析任务：未发起/排队/运行/待补充/失败/建议就绪，复用现有持久任务和预算。
- 结算：未入账/已确认/已撤销或冲正，复用既有实际流水和版本协议。

“结果已确认”与“奖励已入账”是不同字段：未完成可以确认锁定，但没有属性或金币结算，不能为复用只读 UI 就伪标为已入账。完成/部分完成仍走建议后的确认入账。所有最终确认结果收起直接切换按钮，服务端也拒绝覆盖；错点的更正入口另走显式确认/版本历史，不永久禁止修正真实错误。

完成／部分完成显示原计划目标，提供实际投入/完成内容的补充区。用户点“完成”可表达“报告已完成这项计划”，但程序不能凭空编造公里数、配速、学习质量或额外成果；必要资料不足就请求补充，不假造高置信度。

未完成在原卡片显示待确认和“确认未完成”，确认后显示“未完成·已确认”；不要求原因、不弹补充页/成功 toast、不调用模型。去掉原型反复展示的“不自动扣分”解释，确有保存错误仍就近提示。单纯状态不是新生活事件，也不增加事件记录天数。不会单靠该按钮执行 `goal.fail`、挑战失败或固定扣点。未最终确认的完成改成未完成须使旧建议失效；历史原文保留，不能顺手删记录。最终确认后的更正是另一条显式操作，已入账纠正须冲正，不能以切换按钮静默覆盖旧账。

无 Key 时也能保存完成事实；分析/奖励停在待分析，不显示“没有模型所以金币已经为 0”或撤销已保存内容。模型临时失败、取消、过时回写都不丢实际记录。

## 5. 日记关联与防重复

1. 用户主动选已有原文作为这次行动的事实，或从计划生成一条新事件；模型只可建议相关对象，不自动物理合并。
2. 关联记录须属于本人，且事实/日期/状态适用，选择时说明是否已经结算；跨用户引用返回不可见。
3. 原文不会为了勾选完成而覆盖。补充实际用量或结果放版本化补充/派生存档；编辑未确认事实按当前版本失效分析。
4. 同一安排反复修改未入账结果，更新同一次事实/版本并保留变更记录，不每次按钮都新增 Event。
5. 已入账的事实再关联计划，只同步关联/进度展示，不发第二份原事实属性与金币。补充新成果若确属新增行动需单独明确，不能通过换 request_key 重算同一事实。
6. 计划当次身份＋原事实结算身份＋UUID 回执共同防重；不同 UUID 的同一当次动作也不能重复结算。不是只禁用前端按钮。
7. 晚间回顾仅引用完成事实与建议；不能把“总结里又出现一次跑步”当新的领奖事件。

本机 Demo 用显式关联已有原文演示这个区别；它不实现跨数据库语义去重或证明实际 PG 并发已安全。

## 6. 奖励、属性与目标进度

- 按有效投入/成果产出属性建议，主线金币遵循用户已确认的分档方向；与当前非主线行动有差别，但不修改实际属性的科学口径来制造主线金币倾斜。
- 展示实际事实依据、相关目标、基础/主线额外奖励、影响维度和是否仅为建议；用户确认后才出现“已入账”。
- 示例里的 +2/+3/+5 币、+0.2/+0.6 属性**全部是展示占位数值，不是确认的经济算法**，不能复制进 Writer 实现常量。
- 正式金额/上限、基础 2 币是否沿用、主线变更生效点和与挑战/成就叠加仍待确认；没有表就不能启用新经济结算。
- 目标进度要区分“完成次数”“实际数量”“部分完成状态”；不能默认部分完成=0.5 次，未完成更不能因为存了一条 Event 就+1 次。用户未给数值时保留“部分完成”状态，不伪造百分比。
- 实际发生日期、计划日期、保存日期分开；补录跨日时按哪个周期统计必须明确，不再直接以 created_at 充当行动发生日。
- 完成日常行动不自动宣告整个长期目标达成；里程碑/挑战奖励仍走各自协议，保留同事实防重复边界。

最终确认事务应串行核对本人、当次版本、事实/判定版本、规则/主线快照、重复结算身份，属性实际流水/金币流水/审计/回执/当次入账状态同提交；必需写点失败全部回滚，不能先画勾再静默丢账。

## 7. 前后端修正范围

- 新日程和当次模型/迁移，items 入参与返回协议、只读当天计划、结果保存/读取、明确关联已有事实。
- `item_service` 与所有目标进度消费者改为明确的结果/数量统计；不改写旧 Event 历史，旧每周次数口径需兼容方案。
- 既有 Event/AnalysisJob/确认入账中携带当次关联、实际内容、版本快照和主线依据，避免平行发奖。
- `HomeView`/today 接入到期卡片，`ItemManager` 支持日程，`GoalsView` 支持目标行动关联；主入口不是藏在层层设置里。
- `ReviewView` 去心情区、只回看既有事实；详情页/待处理同步任务状态。
- 交易、取消、错误、账号切换、无模型和键盘/窄屏可用性沿用既有保护；普通页面不展示 UUID 等开发细节。

## 8. 代表性验收

| 场景 | 必须验证 |
| --- | --- |
| 周一跑步 | 周一出现，周二不出现；时区与跨日查询一致 |
| 隔一天行动 | 开始日与 +2 日出现，+1 日不出现；跨月/年仍按本地日期算 |
| 弹性每周 3 次 | 保留原语义，不擅自指定三天；剩余次数与完成定义一致 |
| 日记只写愿望 | 不自动创建行动、安排提醒或发奖 |
| 保存完成/部分完成 | 一次事实与明确状态；建议出现前余额/属性不变 |
| 记录未完成/没操作 | 两者不同；原卡片确认，无补充页/成功 toast；确认后 UI 和服务端均不能直接改为完成，不造事件/账目 |
| 新建计划与历史列表 | 没有行动领域必填；周二今日不堆周一旧任务，总计划与历史仍可看 |
| 关联旧日记 | 原文保留、一次事实、已入账不重复奖励 |
| 双击/双设备/异正文重放 | 单次当次状态、单笔实际流水，冲突保留输入 |
| 模型失败/换 Key/编辑晚到 | 原文不丢；旧租约/版本结果不能入账 |
| 确认中途失败 | 当次状态、属性、金币、回执和审计原子回滚 |
| 周期修改/停用/跨期 | 历史保留，新一期不继承上一期“已入账” |
| 回顾再提同一行动 | 不新建领奖事实、不重复金币/属性 |

以上实际应用验收需临时 SQLite、独立 PostgreSQL 多连接/故障注入、真实前端与真机分别留证；Demo 本机浏览器只能验界面和示例脚本，不能代替它们。

## 9. 实施前还要补的决定

- 主线分档金额、上限、实际证据档位、基础奖励/叠加。
- 部分完成的目标进度口径，未入账事实是否先反映行动进度及如何标注。
- 已结束日期能否补记/改结果、日程编辑生效与时区变更策略。
- 无 Key 用户是否除保存外另有无需模型的确定奖励路径；本次确认仅采用建议后人工入账，不自动引入固定打卡奖励。
