# 开发计划 v1.3：判定体验与交互修复（2026-09-05）

> 本文档是本轮开发的唯一需求来源，交给实现 AI 执行。开始前先通读 `docs/PRD.md`、`docs/DECISIONS.md`，并遵守 `docs/WRITER_PROMPT.md` 的全部 Git 工作流规范。与本文档冲突处，以本文档为准；仍不确定的写 TODO 并登记到 `docs/DECISIONS.md`。

## 〇、本轮范围与边界

**做什么**（三个批次，按顺序交付）：
- 批次 A：AI 追问/引导回顾收紧 + 日记维度覆盖自检（prompt 层）
- 批次 B：判定中心审计轨迹刷新修复 + 提交结果预览持久化（前端）
- 批次 C：属性维度开关 UI 整合（前端设置页）

**不做什么**（本轮严禁顺手实现）：AI 接入架构（设置页 API Key / 模型绑定切换 / 免费模型兜底）、首页 AI 问候卡片、语音输入、桌宠、金币商店、多用户登录。这些在 DECISIONS.md 另有排期。

**产品定位提醒**：AI 是「引导者」，但科学客观是底线（见 DECISIONS.md 开头）。追问的首要目的是帮用户回忆、复盘这一天中有意义和价值的东西，加点只是其次——但追问不得变成机械例行公事。

## 批次 A：判定体验增强（prompt 层，最高优先级）

### A1. AI 追问/引导回顾收紧

**背景**：用户 9 条历史判定全部直接判定，`needs_clarify` 无一次为 true——"AI 从不提问、不引导回顾"的反馈属实。根因在 `app/prompts/judge.py`：
1. 「追问引导」节含免问出口："若你觉得某个问题对用户回忆复盘没有意义，就不要问——即便加点信息仍不完整，也不强求"
2. 输出模板默认 `"needs_clarify": false`，模型顺默认值走
3. 「客观性硬约束」"信息不足可下调 confidence 直接判定"与追问条款冲突，AI 全选了直接判定

**需求（用户已确认的尺度）**：
- 日记模式（source=journal）**默认追问**：只要日记有值得回顾的空间就问，只有写得确实充分完整、无明显可回顾内容才可直接判定
- 问题导向：优先引导用户回忆**今天有意义、有价值、印象深刻的事**（开放式问题，如"今天还有什么让你印象深刻或开心的小事吗？""今天的心情怎么样？"）
- 涉及加点准确性的数字细节（时长/强度/频率），AI 看情况追问，不强制
- 结构化打卡（source=form）维持现状不追问
- 多轮追问机制已存在（`ClarifyNeededError` → 前端补充 → 带 clarification 重判），保持兼容

**技术方案**（改 `app/prompts/judge.py`）：
1. 重写「追问引导」节，删除免问出口，替换为明确触发规则：
   - 日记模式默认 `needs_clarify: true`（首轮），除非日记已充分展开且确实没有值得回顾的内容——此时必须在 `analysis` 的"要素解析"中说明"日记已充分、无需追问"的理由
   - 首轮问题优先引导回忆有意义/有价值/印象深刻的内容；数字细节仅在明显影响加点时看情况追加
   - 单轮 1~3 问；用户补充后若仍有值得回顾的空间可继续追问（沿用现有多轮逻辑）
2. 修改「客观性硬约束」第 77 行，消除冲突：信息不足时**必须先追问，禁止通过降 confidence 直接判定**；confidence 只用于表达"信息足够时的判定把握"
3. 输出格式说明中补充 `needs_clarify` 的语义注释（默认 true for journal / false for form，由模型按上述规则判定）

**验收标准**：
- 提交一篇简略日记（如"今天下午专注编程3小时"）→ 返回 `needs_clarify: true` 且问题引导回顾（而非只问数字）
- 提交一篇充分展开的日记（含作息/情绪/事件/感受）→ 可直接判定，且 analysis 中说明免问理由
- 结构化打卡 → 不追问，直接判定
- 多轮追问 2 轮后可正常完成判定入账

### A2. 日记维度覆盖自检

**背景**：用户感觉加点维度少。数据核查：多生活面日记（如睡觉+早饭+跑步+全天状态）只判了 3 维，存在漏判面。

**技术方案**（改 `app/prompts/judge.py`「多属性联动」节 + 分析过程要求）：
1. 增加"生活面覆盖度自检"步骤：判定前先核对日记是否提及以下生活面——作息、饮食、运动、学习/工作、社交、情绪感受、其他（消费/爱好等）——列出**识别到的生活面清单**；对提及但未出现在 `affected_attributes` 的面，必须复核"确实无据可加"才可跳过
2. 「分析过程要求」的 analysis 第 1 步"要素解析"中，要求列出识别到的生活面清单（如"要素解析：识别到作息（睡到8:40）、饮食（买早饭）、运动（跑步2公里）、情绪（状态好）"）
3. 强调这不是强行凑维度：无据的面不硬凑，但要"过一遍脑子"而不是漏看

**验收标准**：
- 对 #11 同类日记（作息+早饭+跑步+状态），analysis 中应列出 ≥3 个生活面，判定维度数 ≥4（饮食/作息面有据则加分，无据则说明）
- 单一事件打卡不因此虚增维度

## 批次 B：前端体验修复

### B1. 判定中心审计轨迹刷新修复

**背景**（09-04 反馈）：审计时间线只显示「生成判定」，后续操作不出现。已确认根因：`frontend/src/components/JudgmentList.vue` 的 `runAction`（确认/补充/反驳/删除成功后）只调用 `load()` 刷新判定列表，**未重拉已展开的审计面板 `auditLogs`**；后端 `_log` 写入点齐全，无需改动。

**技术方案**（改 `JudgmentList.vue`）：
1. 把审计拉取逻辑从 `toggleAudit` 抽成独立函数 `refreshAudit(id)`（拉取并赋值 `auditLogs`）
2. `runAction` 成功后：若 `auditTarget.value === id`，调用 `refreshAudit(id)` 同步刷新
3. `removeEvent` 成功后同样处理（删除后判定消失，此时收起审计面板即可：`auditTarget.value = null; auditLogs.value = []`）
4. 顺带整体核查后端 `judge_service.py` 全部 `_log` 调用点覆盖 confirm / supplement / dispute（含 rejudge、maintain）/ delete 回滚等路径，有遗漏补上

**验收标准**：
- 展开某判定审计 → 点确认入账 → 审计时间线**无需关闭重开**即新增「确认入账」条目
- 补充/反驳后同理；反驳被 AI 维持原判时轨迹出现 `maintain`（维持原判）条目

### B2. 提交结果预览持久化

**背景**（09-03① 反馈）：`EventForm.vue` 的 `result`/`clarifyEvent` 是纯内存 ref，跳转其他 tab 后回来全部重置，判定结果丢失。

**技术方案**（改 `EventForm.vue`）：
1. `result` 与 `clarifyEvent`（含 questions）状态持久化到 `sessionStorage`（key 如 `gol_last_judgment`），提交成功/追问发生时写入，`reset()` 与新提交开始时清除
2. 组件挂载（onMounted）时从 sessionStorage 恢复，切页返回不丢
3. result 卡片中增加一个「去判定中心确认 →」按钮，点击后切换到判定中心 tab（通过 emit 事件让 `App.vue` 切 activeTab，或用现有 tab 切换机制）
4. 追问进行中（clarifyEvent 非空）切页再回来，问题列表与输入状态同样恢复

**验收标准**：
- 提交日记得到判定结果 → 切到属性面板再切回 → 结果仍在
- 追问中切页再回 → 问题卡仍在可继续回答
- 点「去判定中心确认」→ 正确切 tab；确认入账后回记录页，旧结果已清除

## 批次 C：属性维度开关 UI 整合

**背景**（09-03③ 反馈）：设置页 13 维 × 3 按钮（显示/隐藏/关闭判定）共 39 个按钮太冗余。**注意：三态开关功能本身已实现**（`SettingsView.vue` 的 `stateOf`/`setState`，后端 settings 存储），本轮只做 UI 整合，不改后端存储结构与语义。

**需求**：整合为紧凑布局，同时执行 DECISIONS.md 已确认的开关语义：显示（默认）/ 隐藏（AI 照判不显示）/ 关闭判定（冻结，重开不校准从当前值继续）。

**技术方案**（改 `SettingsView.vue`，方案可微调但需保持"一眼看清非默认维度"）：
1. 每维度一行，3 个按钮改为**单个下拉选择**（select：显示/隐藏/关闭判定）
2. 默认只展示**非默认状态**（隐藏/关闭判定）的维度；其余维度收进"全部 13 个维度"折叠区（`<details>` 或简单 v-if 展开），减少视觉噪音
3. 顶部保留一句语义说明（现有第 164 行文案保留）
4. 状态变更即时保存（沿用现有 setState 逻辑），保存成功有轻提示

**验收标准**：
- 设置页无 39 按钮阵列；默认视图只显示用户改过状态的维度
- 切换任一维度状态后刷新页面，状态保持；关闭判定的维度在后续判定中不被加点（可提交事件验证 analysis 中提及不判定该维度）

## 交付与工作流要求（强制）

1. **分批提交**：每批次完成后单独 commit，message 中文（`fix:`/`feat:`/`refactor:`），一个 commit 一个逻辑单元；只 commit，**不 merge、不 push**
2. **每批自验后再交付下一批**：
   - 后端改动：`py_compile` 语法检查 + 隔离环境加载 `app.main` 成功
   - 前端改动：`npm run build` 零错误
   - 批次 A 需真实调用 DeepSeek 验证 prompt 效果（若环境无 key，写明"待用户实测"并给出 3 条测试日记建议）
3. **一键启动**：改完后确认 `start.bat` 仍可一键起前后端
4. **文档同步**：完成后在 `docs/DECISIONS.md` 将对应 backlog 条目标记 `[x]` 并附实现摘要（含日期）；README 如有 UI 变更同步更新
5. **禁止事项**：不提交 .env / *.db / node_modules / .workbuddy；不改本轮范围外的任何行为；prompt 改动只动 `app/prompts/judge.py`，不碰其他 prompt 文件
