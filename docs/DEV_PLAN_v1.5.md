# 开发计划 DEV_PLAN v1.5（判定链路统一 + 数据一致性 + 稳定性）

> 交付对象：实现者（writer）。开工前先读 `docs/PRD.md`、`docs/DECISIONS.md`（backlog 全文，含 2026-09-08 晚用户实测反馈）、`docs/WRITER_PROMPT.md`。本文档是本轮唯一范围依据。

## 根因定位（2026-09-09 已实测确认，实现前必读）

用户反馈"刷新后判定中心与上传日记时的判定不一致"，根因在**追问补充的链路设计**：

- EventForm 的追问补充走 `POST /events/{id}/judge`（带 clarification）→ `judge_event()` 内部逻辑（judge_service.py 约 L221-251）：**事件已有未确认判定时，先删除旧判定（连同其全部审计日志 JudgmentLog）再新建一条判定**。
- 后果链：①每轮追问补充都删旧建新，新判定由 LLM 重新生成（temperature 0.3 + 上游偶发抖动），维度/加点随机漂移——首判有情商、重判没有（或反之），即用户看到的"DeepSeek 持续分析导致结果变动"；②旧判定的审计历史被连带删除，审计轨迹不完整（用户反馈的"审计异常"）；③判定 id 每次变化，前端残留的旧 id 引用（auditTarget、sessionStorage 预览）失效错乱；④EventForm 的 sessionStorage 预览停留在首判结果，与 DB 现行判定不一致——用户"上传时看到的"与"刷新后看到的"分叉。
- 另一条重判链路 `POST /judgments/{id}/supplement`（判定中心入口）则是**就地更新同一条判定**（id 不变）——两条链路行为不一致，是混乱的根源。
- `runAction(id, fn, okMsg)` 的 `okMsg` 参数传了从未使用 → 成功无任何提示（用户反馈"无成功提示"实锤）；补充/反驳文本只写进审计日志，判定卡不展示。

本轮核心思路：**一条事件只保留一条现行判定，重判一律就地更新、审计只增不删，展示端统一以 DB 现行判定为唯一数据源。**

## 批次 A（P0 · 判定链路与数据一致性）

### A1 统一重判链路：重判一律就地更新，禁止删旧建新

- `judge_event()` 的 clarification 分支：不再"删除旧判定（连同审计）再新建"，改为**就地更新现行判定**（与 `supplement()` 相同模式：更新 suggested_changes/analysis/summary/confidence/confidence_reason/status，id 不变），审计日志追加一条 `rejudge`（带 clarification 摘要），**任何情况下不得删除 JudgmentLog**（除事件删除级联外）。
- "先清后建"仅保留一种合法场景：事件被**编辑**（`PUT /events/{id}`）后旧判定作废——此时旧判定及其审计**归档保留**（status 置 `invalidated` 并在审计记一条 `invalidate`），而非物理删除；新增判定与事件重新判定。STATUS_LABEL（JudgmentList.vue）同步加 `invalidated: '已作废'` 标签。
- 全局 grep 确认 `JudgmentLog` 的 delete 调用点，除 `delete_event` 级联外全部移除。

**验收**：同一事件连续 3 轮追问补充 → 判定 id 始终不变，审计轨迹完整记录 create→clarify/supplement→rejudge 全程；任何操作后刷新，判定中心、手账本、审计面板三者数据一致。

### A2 提交反馈与提交内容展示

- `runAction` 成功路径真正使用 `okMsg`：成功后就地轻提示（操作按钮旁 2 秒成功态文字或轻量 toast，禁止阻塞式 alert 用于成功场景；失败仍用现有就近 actionError）。
- 判定卡展示最近一次用户提交的补充/反驳内容：数据源用审计日志（该判定最新一条 supplement/dispute 的 detail），判定卡新增折叠区「我的补充/反驳」默认收起，点击展开显示内容与时间。
- 补充/反驳提交成功后，若该判定审计面板已展开则同步刷新（现有 refreshAudit 逻辑保留）。

**验收**：提交补充 → 按钮旁出现"已重新判定"轻提示，判定卡可看到自己刚提交的文本；提交反驳 → 同样有反馈及 AI 复核结论展示（现有 alert 结论逻辑可改为就地展示）。

### A3 单一数据源：各模块统一读 DB 现行判定

- EventForm 的 sessionStorage 预览（key `gol_last_judgment`）：存入 `judgment_id`；组件恢复预览时校验该 id 是否仍是事件现行判定（新增轻量接口或在现有响应中带 judgment_id），不匹配则丢弃预览并提示"判定已更新，以判定中心为准"。
- 核查并统一 4 个展示端的数据来源（一律读 DB 现行判定）：EventForm 结果卡 / JudgmentList（判定中心）/ TimelineView（手账本）/ 日记事件记录列表。交付时在 PR/README 附一张「模块 × 展示字段 × 数据来源」对照表。
- 判定卡显示重判次数（如"已重判 · 第 2 次"，从审计日志统计 rejudge+clarify 次数）。

**验收**：上传日记→追问补充→刷新页面，判定中心与上传时最终看到的判定一致；EventForm 旧预览被正确失效并提示。

### A4 审计与编辑功能异常排查修复

- 与 A1/A3 同链路核查：审计面板展开状态下做补充/反驳/删除/编辑，逐一实测轨迹刷新与残留；编辑事件→判定作废（A1 新逻辑）→审计面板的展示。
- `openEdit`/`saveEdit` 链路：编辑回填、保存成功提示、判定作废后的界面状态刷新。
- 发现的具体 bug 逐一登记 DECISIONS.md（表现+根因+修复），不许模糊带过。

**验收**：审计/编辑全操作矩阵实测无残留、无 404、无幽灵 id；审计时间线按时间正序完整可读。

### A5 LLM 偶发空返回自动重试

- `llm_service.chat_json`：对空 content（及"解析后无有效字段"）做 1 次自动重试（指数退避 ~1s），重试仍失败才抛 LLMError。重试幂等安全（A1 后重判为就地更新，无重复建行风险）。
- 失败时前端提示文案统一含"AI 服务偶发抖动，已自动重试仍失败，请稍后重试"。

**验收**：模拟空返回（mock）触发重试并成功；连续两次空返回 → 前端收到明确错误且输入内容保留（结合批次 B 前置检查）。

## 批次 B（P1 · 体验优化）

### B1 判定中心按日期分组折叠

- 分组：**今天 / 昨天 / 本周更早 / 更早**（按判定 created_at 日期，组头显示"周X MM-DD + 条数"），组内按时间倒序。
- 每条判定默认**收起为一行摘要**：标题 + 状态标签 + 置信度 + 时间；点击展开详情（分析过程/加点明细/操作按钮/审计）。
- 组头可折叠：默认展开「今天」，其余组默认收起；记住用户的展开状态（localStorage，按组 key）。
- 保留现有搜索框（搜索命中时自动展开匹配项所在组）。

**验收**：20+ 条历史记录时页面首屏只显示分组头与今天组摘要行；点击展开流畅；搜索"跑步"能命中并自动展开。

### B2 分析维度完整性与加点稳定

- **temperature 0.3 → 0.2**（`app/config.py` llm_temperature 默认值；0=完全确定但措辞呆板，0.3=漂移明显，0.2 为平衡点；用户已确认降温度方向，具体值如需微调改一处配置即可）。
- judge prompt 新增**输出前维度硬校验**：输出前对照全部现行属性（从注入的属性上下文）+ 生活面清单逐维自检——识别到生活面而无对应加点 → 必须在要素解析说明"无据"理由；禁止同一事件两次判定维度数明显缩水。补充重判时**不得丢失首判已识别的维度**（重判 prompt 中注入首判的 affected_attributes 清单，要求：除非有明确依据撤销，否则保留）。
- 结合 A1（重判不再随机重建）后，"持续分析结果变动"自然消失：判定只在用户操作时更新。

**验收**：同一篇日记判定 3 次（删判定重测），维度集合一致或差异均有"无据"说明；重判不丢维度。

## 统一约束

- **禁区**：桌宠、金币商店、语音输入、首页问候卡片、多人联动、M4 上云/MySQL、AI 接入架构（v1.4 已完成，勿动）。
- **Git**：只 commit 不 push；一个逻辑单元一个 commit，中文 message；严禁提交 `.env`、`*.db`、`node_modules/`、`.workbuddy/`。
- **数据红线**：库里有真实数据；本轮**禁止物理删除任何判定/审计历史数据**（A1 归档方案）；如需表结构变更走启动时自动迁移（v1.4 已有通用迁移函数），禁止要求删库。
- **自验**：每批次——后端 py_compile + 隔离环境启动冒烟；前端 `npm run build` 零错误；批次 A 必须用真实 DeepSeek 调用走通"上传→追问→补充→重判→刷新核对"全流程并报告实测结果；批次 B 需 20+ 条记录下实测折叠/搜索。
- 完成后回写 `docs/DECISIONS.md` 2026-09-08 晚 backlog 条目（①~⑤）与「LLM 调用稳定性」为 `[x]` 并附实现说明；不确定处保守实现 + TODO + 登记 DECISIONS.md。

**交付顺序**：A1 → A5 → A2 → A3 → A4 → B1 → B2（A1 是根因修复最优先；A5 早做减少验证干扰；B 批次最后）。预计每批次交付后用户可独立实测。
