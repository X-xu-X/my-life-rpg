## 0. 先明确现在能做什么

目标是：手机通过固定HTTPS网址使用，所有者电脑关机也能记录；每个账号的数据和模型Key独立；云机损坏后能从独立备份恢复。

**当前代码不能直接安全地部署给朋友。** 它仍使用default用户、自由日记保存前调用AI、模型Key明文配置、SQLite专用备份和开发代理。登录隔离、PostgreSQL迁移、生产镜像/Compose、后台worker与运维脚本尚未交付。本文是准备和将来部署的操作合同，不代表这些能力已实现。

现在可以完成第1–4节的选择、账号与成本准备，并在获得具体采购授权后创建资源；第5节的应用交付门槛通过前，不上传真实数据库、不发邀请、不把开发服务器开到公网。本轮只写文档，没有购买、部署、安装或迁移。

本文命令均为将来执行的示例，未在本轮运行。命令块标注执行位置；`<DOMAIN>`、`<SERVER_IP>`、`<RELEASE_ID>` 等必须替换，不能原样粘贴。任何可能写数据的步骤必须在明确目标环境按门槛执行。密码、私钥、API Key、会话令牌和包含秘密的配置不粘贴到聊天、不提交Git、不写截图。

## 1. 推荐起步配置与地域选择

### 1.1 起步架构

推荐一台2核4GB Ubuntu LTS Linux云机，Caddy入口、静态Vue前端、FastAPI和PostgreSQL同机；B阶段再运行同机单worker，分析全局并发先为1。数据库任务表代替首批Redis/队列服务。数据库/API不开放公网端口。每天备份到独立私有对象存储，并离线另存凭据主密钥。

这是节省费用的单机方案，没有高可用：云机维护、磁盘故障或整机故障可能停机。先测内存/磁盘/响应再扩容；云端不现场编译前端，不装GPU。首批不买CDN、负载均衡、媒体套餐、短信、商业证书或托管数据库。

后续若运维或可用性压力超过能力，再比较托管PostgreSQL、应用与数据库分机及PITR。托管数据库带来额外费用、网络/权限/备份配置；迁出同机数据库必须另做迁移演练。SQLite过渡的限制见开发计划第4节，不能只换连接串自称已支持PostgreSQL。

### 1.2 中国内地与香港比较

| 事项 | 中国内地地域，例如广州 | 中国香港地域 |
|---|---|---|
| 适合情形 | 主要用户在内地，愿意按流程准备域名及备案 | 希望先评估较快开通，接受跨境连接和数据地域选择 |
| 用户访问 | 通常更适合内地用户，仍须用朋友手机实测 | 不能承诺比内地快；腾讯云香港入门套餐说明跨境时延/丢包风险，不保障跨境网络质量 |
| 备案 | 内地提供网站服务按要求办理ICP备案；个人/企业主体与服务范围核对 | 腾讯云说明香港服务器无需内地ICP备案；这不等于隐私、数据跨境、AI服务等义务一并免除 |
| 外部模型 | 单独测试所选供应商API的可达性、地区和服务条件，不靠任意代理绕行 | 同样需要测试，香港部署不保证所有模型可用 |
| 数据位置 | 日记、数据库、备份地域需明确；模型请求可能另去供应商地域 | 用户需知道日记/备份在香港，模型请求还可能跨其他地域 |
| 后续迁区 | 视为迁移：停写、导出、恢复、DNS切换和账目验证 | 同左，不假设原套餐可一键原地变地域 |

推荐先把广州作为内地用户的候选，香港作为另一个有明确网络/数据取舍的候选；**最终地域由所有者在采购前选择**。用本人和朋友常用运营商/蜂窝网络实测，不能用所有者电脑一次ping代替手机页面和模型测试。

依据：[腾讯云轻量应用服务器价格与地域说明](https://cloud.tencent.com/document/product/1207/73452)、[腾讯云ICP备案概述](https://cloud.tencent.com/document/product/243/19630)。网站在内地上线后，公安联网备案相关流程及时限参见[腾讯云公安备案说明](https://cloud.tencent.com/document/product/243/18910)；官方说明涉及开通后30日要求，应在上线前核实当前主体、地域及当地办理口径。邀请制不自动豁免这些要求，使用IP/非标准端口也不能当作备案替代。

云主账号仅由所有者保管；实施者如需访问，创建最小权限子账号/临时授权，部署后撤销。对象存储桶保持私有，备份身份限制指定前缀操作；避免给应用进程整个云账号权限。数据库使用业务账号、迁移账号和备份账号的合理分工，具体授予足够但最小的权限并验证，不以超级用户跑所有业务。

## 4. 步骤一：账号、地域、域名与合规准备

**目的：**在花钱和上传日记前确定责任、地域及实际费用。  
**位置/入口：**所有者电脑，腾讯云官网控制台的账号安全、轻量应用服务器购买页、域名注册/备案入口。界面名称变化时使用站内产品搜索，不跟来历不明的代购链接。

1. 登录自己的云账号，完成所需实名，开启MFA，核实邮箱/手机可用于恢复；使用密码管理器，不共享主账号。
2. 对比第1–2节两种地域，在订单中记录完整SKU和续费费用；先不点支付，形成可评审采购清单。
3. 查域名可注册性、首年/续费和隐私选项，排除溢价域名。域名所有者与备案主体按规则匹配。已有可用域名可规划子域如`life.example.com`，确认控制权。
4. 内地方案核对ICP备案资格、服务器与域名要求、网站服务范围及公安备案安排；公众/商业/平台代付AI拓展前重新核对服务要求。香港方案明确数据地域和跨境网络取舍；不承诺任何地域免除全部义务。
5. 获得具体采购确认后才下单；初次实测前优先短周期。保存非敏感订单记录、续费日期和资源ID。

**成功标志：**有明确地域、域名控制权、实际价与续费价、备案路线、预算和责任人。  
**常见失败：**域名已占用→换普通候选；主体不符/备案条件不足→先解决或重新评审地域；报价超过预算→调整候选并给具体订单，不擅自缩水备份。

## 6. 步骤三：云机、安全入口与运行环境

**目的：**提供最小网络暴露、可登录且重启可恢复的运行环境。  
**位置：**云控制台与服务器Linux终端；不在Windows里执行Linux安装命令。

1. 按已批准订单创建Linux实例，优先选择Docker官方支持的Ubuntu LTS版本，记录发行版、地域、资源ID、公网IP与盘容量。系统软件版本要与实施者测试组合一致。
2. 云防火墙先仅允许管理来源IP的SSH 22；网站准备开放时放行80/443。不要开放5432、8000、5173；变动管理IP先核实来源并更新规则，不能为省事长期开SSH到全网。
3. 生成/使用受保护的SSH密钥，在云控制台安全配置登录；首次核对服务器指纹。建立具备所需sudo权限的部署身份，验证密钥登录后再调整密码登录，保留控制台救援入口，避免锁死自己。
4. 安装系统安全更新与Docker Engine/Compose插件，按[Docker官方Ubuntu安装说明](https://docs.docker.com/engine/install/ubuntu/)执行与发行版匹配的步骤；不要运行来历不明的一键脚本。加入docker组相当于高权限，限制成员。
5. 实施者创建版本、持久数据和受限配置目录；磁盘持久路径与容器挂载按照锁定PG镜像版本确认，特别不能照抄其他PG大版本的挂载目录。权限最小化，配置不进Web静态目录。
6. 开启主机资源/磁盘/费用告警；日志轮转限制总量；核实系统时间同步。暂不配置自建公网代理、媒体服务或多实例。


**常见失败：**SSH超时→检查IP、来源限制与实例状态；权限不足→由管理员按最小权限修正；Docker不兼容→回官方对应发行版说明；不要直接关闭全部防火墙。

## 7. 步骤四：发布包、秘密、数据库与空库应用

**目的：**先用空库证明生产包可以运行；真实SQLite不是这一步的输入。  
**位置：**实施者构建环境与服务器Linux终端。

### 7.1 发布包和配置

构建环境按锁定依赖生成Vue静态产物和应用镜像，标记不可变发布ID/摘要；发布包不含`.env`、本地SQLite、备份、日志和个人Key。服务器目录推荐 `/opt/game-of-life/releases/<RELEASE_ID>/`，每个版本单独保留；持久数据不得放在被新版本替换的目录内。

实施者根据实际 `.env.production.example` 创建 `/etc/game-of-life/production.env`，限制到部署所需身份可读；凭据主密钥单独放 `/etc/game-of-life/secrets/`，离线保存副本。环境文件可能含数据库DSN等秘密，不能 `cat` 发给聊天或在故障截图中展示。容器内秘密的读取方式与UID授权必须由生产包实现并验收，不能把主密钥硬编码在镜像。

| 配置类别 | 必须明确的值/约束 |
|---|---|
| 运行模式 | 明确云模式；不创建default、不读取个人全局模型Key、不自动迁移；启动缺配置失败。具体新增字段由实现包定义，当前源码尚无完整云模式 |
| 数据库 | 当前应用字段名为 `DB_URL`；目标为已验收的PostgreSQL驱动URL；区分业务/迁移/备份权限；不得误用不存在的 `DATABASE_URL` 以为已切库 |
| 身份/会话 | 真实域名、Secure/HttpOnly Cookie、CSRF/Origin策略、会话过期、邀请/恢复；不是仅设置跨域白名单 |
| 凭据 | 加密主密钥文件位置、key_id及轮换/备份策略；API Key属于用户配置，不能在平台env给所有人兜底 |
| 模型调用 | 批准供应商端点、连接/总超时、总重试预算、并发/每日限额；所有调用链统一生效 |
| 时区 | 服务和数据库以UTC存新时间；用户默认Asia/Shanghai；旧无时区时间按明确迁移策略解释 |
| 持久化 | 数据库、证书、日志/备份临时目录的挂载与保留；最终PG镜像实际数据目录核对，不用临时容器层存数据库 |
| 任务 | A同步模式或B持久worker；B需租约/重试/停止策略，不能仅配置进程名就宣称恢复能力 |

云端不要沿用 `start-phone.bat`、Vite dev server、`uvicorn --reload` 或直接开放8000端口；正式前端由入口服务静态文件，浏览器只访问同域 `/api`。

### 7.2 空库部署的条件命令

以下是**后续生产包的约定示例**：Compose服务须由实施者交付并核实为 `db`、`api`、`caddy`，B才增加 `worker`；API镜像须支持 `python -m alembic` 且工作目录正确。若真实交付名称/入口不同，先按已验收README修订命令，不盲目执行。

```bash
# Linux服务器；仅在第5节通过、占位符已替换、目标确认为空预发库后执行
# 配置检查不展开输出，避免泄漏环境变量
sudo docker compose --env-file /etc/game-of-life/production.env -f /opt/game-of-life/releases/<RELEASE_ID>/deploy/compose.prod.yml config --quiet

# 初始化空库：有写入，只对确认的预发/新部署目标执行
sudo docker compose --env-file /etc/game-of-life/production.env -f /opt/game-of-life/releases/<RELEASE_ID>/deploy/compose.prod.yml up -d db

# 只读检查db健康；未healthy不执行迁移
sudo docker compose --env-file /etc/game-of-life/production.env -f /opt/game-of-life/releases/<RELEASE_ID>/deploy/compose.prod.yml ps

# 单独迁移；先检查目标DSN身份，失败立即停止后续发布
sudo docker compose --env-file /etc/game-of-life/production.env -f /opt/game-of-life/releases/<RELEASE_ID>/deploy/compose.prod.yml run --rm api python -m alembic upgrade head

# 启动应用/入口；域名证书待下一节验证
sudo docker compose --env-file /etc/game-of-life/production.env -f /opt/game-of-life/releases/<RELEASE_ID>/deploy/compose.prod.yml up -d api caddy
```

Compose的 `depends_on` 本身不证明数据库已就绪；需健康检查条件，并处理运行中连接失败，参考[Docker Compose启动顺序说明](https://docs.docker.com/compose/how-tos/startup-order/)。迁移应是独立步骤，API/worker启动不能各自竞争改schema。数据库大版本升级另走专门方案，不以拉取新PG镜像更新旧数据卷。

所有者初始账号/邀请通过交付的受限CLI初始化；README必须说明身份、一次性凭据交付及审计。本文件不提供尚不存在的CLI命令，也不要求在SQL里插一个绕过密码哈希的管理员。无公网调试登录入口，不留“测试密码”。

**成功标志：**空库迁移头正确、DB/API健康、无默认公共账号、重建应用容器后数据仍在，日志没有秘密/正文。  
**常见失败：**连接拒绝→核对私网服务名/健康/权限；DB_URL仍指向SQLite→停止并修配置；迁移错误→保留日志和目标，不继续启动；磁盘/UID错→按镜像要求修挂载与权限，不删卷试错。  
**下一步：**配置DNS和HTTPS，再用两个空测试账号验收。

## 8. 步骤五：域名、HTTPS与手机可达性

**目的：**给用户一个固定安全网址，并满足会话Cookie/PWA前提。  
**位置：**域名DNS控制台、云防火墙、服务器入口配置、手机浏览器。

1. 已按地域完成必要的备案准备后，给选定子域添加A记录到该云机公网IPv4；只有确认IPv6全链路正确才加AAAA。避免遗留错误AAAA导致部分手机访问失败。
2. 修改交付Caddyfile中的站点域名为真实域名，确认 `/api` 转发和前端路由回退策略；只服务发布目录中的静态构建，不能把项目根目录整体暴露。
3. 云防火墙允许80/443；核对本机防火墙规则。Caddy配置/证书存储持久化，域名解析可达后获取/续期证书，参考[Caddy自动HTTPS说明](https://caddyserver.com/docs/automatic-https)。不要将“浏览器可忽略证书错误”作为验收。
4. 用Windows核对解析和TLS，用本人/朋友手机Wi-Fi及蜂窝网络打开站点；测试登录、保存、回看、退出。内地/香港候选的实测记录包含网络、页面耗时、失败率，而非只截图首页。
5. 证书续期和域名到期告警单独确认；默认HTTP跳转HTTPS，浏览器不出现混合内容；会话Cookie及CSRF验证实际生效。PWA图标/安装提示可用，但不承诺各平台相同安装入口或可靠离线同步。

```powershell
# Windows PowerShell：只读查询；替换真实域名
Resolve-DnsName '<DOMAIN>'
curl.exe -I 'https://<DOMAIN>/'
```

外网首页返回成功并不能证明API/会话健康；必须在浏览器实际保存和回看一条空测试账号记录，再做双账号隔离验收。健康接口应只给必要状态，不输出DSN/Key/版本内部细节或个人信息。

**成功标志：**域名解析正确、可信证书、HTTPS和同域API正常，手机蜂窝可登录/保存，非预期端口从公网不可达。  
**常见失败：**DNS尚未生效→核查权威记录/TTL；证书签发失败→核对A/AAAA、80/443、域名和CA限额；登录循环→核对Secure Cookie/真实Origin/反向代理；API404→核对路径映射，不能改回公网直连8000绕过。  
**下一步：**独立备份和恢复演练。没有演练不得导入本人唯一真实库。

## 9. 步骤六：独立备份与恢复演练

**目的：**证明失去原服务器后仍能恢复日记、账目、账号及凭据解密能力。  
**位置：**服务器备份任务、独立私有存储、独立恢复环境；不是在生产库上试恢复。

### 9.1 备份内容、保留与权限

初期建议每天一次PostgreSQL逻辑备份，远端留7份日备份+4份周备份；周备份为相应日备份的保留策略，避免含糊地无限累积。实际压缩容量、成功耗时和最旧可恢复时间记入报告。本机可留短期副本，但整机快照、本机目录、与DB同盘文件都不算独立副本。

数据库备份包括全部业务表、schema/迁移版本、账号/会话/已加密凭据，因此仍是敏感资产；使用私有桶、受限身份、传输加密与适当静态/客户端加密。角色/授权创建方式、生产包版本/摘要、非秘密配置及恢复README另备份；数据库dump不自动包含所有服务器角色和文件。主密钥单独离线备份并记录key_id，不和同一下载链接公开。

应用用户JSON导出方便个人带走日记，但不是生产恢复备份：它不应包含认证密钥/全用户信息，也不能覆盖DB约束、迁移和完整运行配置。原有SQLite backup接口到PG可能返回None，必须由A09改正，不能拿旧“status:ok”当成功凭证。

### 9.2 技术命令的边界

优先执行已验收的 `ops/backup.sh` 和 `ops/restore-rehearsal.sh`，参数以正式README为准；定时器按实际部署身份配置。脚本应失败非零退出并告警，不能上传失败后仍更新“最后成功时间”。备份上传完成后核对校验和，记录时点/版本/容量；下载恢复路径要实际可用。

以下仅解释脚本应采用的PostgreSQL工具。**前提**：在受限运维环境已经安装匹配服务器版本的客户端，管理员已配置 `pg_service.conf` 和受限口令文件（不把密码放命令行），`gol_backup` 指向获授权的源，`gol_restore_test` 指向**已创建的全新隔离恢复库**；源/目标服务名只是运维约定，不是当前项目配置。对加密远端备份先按已验收流程解密到受限临时目录。

```bash
# Linux运维环境：读取源库，写本地备份文件；绝不覆盖唯一已有副本
pg_dump --format=custom --file='<NEW_LOCAL_BACKUP_PATH>.dump' --dbname='service=gol_backup'

# 只读列出已下载并解密的备份目录；这不是恢复成功证明
pg_restore --list '<DOWNLOADED_BACKUP_PATH>.dump'

# 有写入：只允许明确的新隔离库，不允许指向生产
# 不使用--clean覆盖生产；失败整体退出
pg_restore --dbname='service=gol_restore_test' --no-owner --no-privileges --single-transaction '<DOWNLOADED_BACKUP_PATH>.dump'
```

参考 [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)、[pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html)。恢复时使用匹配的客户端与目标版本；`--no-owner --no-privileges` 后由运维明确恢复所需业务授权。上述示例没有包含桶上传、备份加密、校验、定时器和告警，不能当作完整备份系统。

### 9.3 一次真正的演练

1. 在预发生成记录/判定/金币/挑战/模型配置等样本，运行完整备份并上传；从远端重新下载，不直接拿原服务器临时文件代替。
2. 用独立环境/新目标库恢复，按配套发布版本启动应用；恢复角色、必要配置和离线主密钥。演练环境不开放给朋友，不向真实模型发送正文来“验证”凭据，采用受控无敏感测试或仅解密完整性检查。
3. 核对17张旧表和新增表的行数/归属/关系，抽样原文、审计、余额/流水/挑战状态；验证可登录、可读记录、加密凭据可用、新写入正常且不污染生产。
4. 记录备份实际时点、恢复开始/完成时间、损失窗口、脚本/镜像/迁移版本、异常及处理。演练目标首批RPO≤24小时、RTO≤4小时，实测未达到就改方案；目标不是保证。
5. 清理演练资源须在另获明确操作授权后针对已核对目标执行；生产备份保留策略由任务自动按已确认规则管理，不在手工排错时随意删。

**成功标志：**从独立副本恢复后完成应用/数据/权限/账目验证，而非仅有一个dump文件。  
**常见失败：**缺主密钥→Key不可解密，先核对key_id与离线材料；备份权限不足→按错误补最小授权；目标非空/版本不兼容→新建正确隔离目标再演练，不用生产库试错；容量超限→调整保留/预算且保留最后有效副本。  
**下一步：**决定本人真实数据是否迁入；也可先空库小范围试用，不强迫迁移旧账。

## 10. 步骤七：本人真实SQLite数据迁移

**目的：**把本人历史归属到明确账号，保留账目与审计，不把旧default数据公开给朋友。  
**位置：**本人电脑上的授权冻结副本、隔离导入环境、经确认的正式目标。由实施者操作并交报告，所有者决定异常方案。

Windows可只读记录冻结副本哈希示例：

```powershell
# Windows PowerShell：仅对已明确的冻结副本；不猜测真实数据库位置
Get-FileHash -Algorithm SHA256 -LiteralPath '<FROZEN_SQLITE_COPY_PATH>'

```

**成功标志：**所有差异可解释、本人账号独占历史、朋友账号为空且独立、原文件/独立备份保留，用户抽样回看关键记录通过。  
**常见失败：**异常/金额不符→停止切流并提交差异；凭据迁移失败→保留原源和日记，可由本人重填Key，不改明文兜底；回退需要新写入→先保存再制定补录，不宣称无损。  
**下一步：**完整上线门槛验收，通过后才发邀请。

**成功标志：**上述报告有实际证据，朋友独立使用且理解边界；上线人、版本、时间、备份时点明确。  
**失败处理：**暂停新邀请/相关功能，保留数据和证据；隔离问题先关闭公网入口或进入维护，不回退无登录旧版。  
**下一步：**持续运维和反馈；B/C按独立验收再发布，不随首批上线自动启用新规则。

## 12. 日常运行、故障定位与费用控制

### 12.1 最少运行清单

| 周期 | 查看/动作 | 通过标准 |
|---|---|---|
| 每天自动 | 备份成功时点/上传校验/失败通知、健康、磁盘、任务积压、错误率 | 不是只看“服务running”；最近可恢复时点在目标窗口内 |
| 每周人工 | 费用/流量、日志总量、证书/域名到期、数据库增长、失败任务与朋友反馈 | 找到异常调用和磁盘趋势；无正文/Key日志；有明确处理人 |
| 每月/重要升级前 | 从独立副本抽样完整恢复、核对密码/密钥恢复材料、复查权限和版本更新 | 应用可读写/核账，不只是备份文件存在；记录耗时 |
| 邀请扩量前 | 模型调用/内存/DB锁/响应、预算和支持能力 | 先测再增加并发/套餐；公众开放另评估服务义务 |

分析请求预算由应用控制“每用户并发/每日调用+全局并发+总重试”，保存请求另设合理频率，不因AI日额度耗尽阻止记录。模型测试、补充、复核、报告、记忆同样计入实际调用；用户供应商自己的预算设置仍需配置，不能把应用配额当充值止损保证。

应用日志记录请求/任务ID、状态、耗时、脱敏错误分类，不记录日记正文、完整prompt、Key、Cookie、DSN。分享排障输出前脱敏；不直接提交 `docker inspect`、完整env、Compose展开配置或全量日志。备份与财务审计属于受限数据，保留期另有策略，不和普通调试日志混为一谈。

### 12.2 常见故障的第一步

| 症状 | 先核查 | 恢复方式/禁止捷径 |
|---|---|---|
| 网站打不开 | 域名解析/证书、主机状态、防火墙、入口容器健康 | 保持数据卷，修网络/入口；不公开数据库/API端口绕行 |
| 保存失败 | API/DB健康、磁盘、用户身份、请求ID及提交是否已落库 | 按UUID查询后重试，不重建整条事件碰运气 |
| 保存好但分析失败 | 本人配置是否过期、供应商余额/429/超时、端点可达、总重试预算 | 保留原文，用户改Key/稍后重试；不改用所有者Key |
| 任务卡住 | B阶段worker健康、租约/重试时间、版本是否已过期 | 受控接管/重试；旧任务不能强制写回新事件，无限重启无效 |
| 磁盘接近满 | 数据/日志/备份缓存增长，独立备份最新成功时点 | 先保留有效副本并扩容或按既定策略轮转；不删数据库目录/唯一备份 |
| 备份失败 | 凭据权限/桶状态/网络/空间/客户端版本/退出码 | 立即处理并补成功备份，延误超过目标窗口告知；不能修改状态假报成功 |
| 登录丢失/恢复失败 | 时间、Cookie域/HTTPS、会话过期、恢复码状态 | 使用正式恢复流程；管理员不能用SQL改成无密码登录 |
| Key无法解密 | 主密钥挂载/权限、key_id/轮换、备份对应离线密钥 | 修复密钥材料；仍可记录；必要时本人重填Key，不重写明文存储 |
| 金额/属性异常 | 停相关写入、保存受限快照，核对结算/流水/历史和版本 | 在隔离副本定位，制定修复/追加更正；不手改余额清理证据 |

服务器只读状态命令示例仍以前述交付契约为前提：

```bash
# Linux服务器：替换实际发布ID；不打印配置内容
sudo docker compose --env-file /etc/game-of-life/production.env -f /opt/game-of-life/releases/<RELEASE_ID>/deploy/compose.prod.yml ps
df -h
free -h
```

查日志、重启单个服务、更新密钥属于具体排障操作，按实际README执行并验证影响；不要默认把应用重启等同数据库重启。主机重启后核对入口、DB持久化、任务/备份定时器、系统时间和证书存储，不只看SSH能连。

## 13. 更新、停止与回退

### 13.1 一次正常更新

**目的：**用可验证的版本替换应用，保留数据与可回退路径。  
**位置：**预发先执行，生产再按维护窗口执行；所有者批准具体发布。

1. 记录旧/新镜像摘要、schema版本、变更范围和回退兼容表；先在独立预发升级并跑相关验收，生产库不做故障注入。
2. 确认最新独立备份可恢复，必要时立即追加备份；告知维护窗口，停止相关写入/worker接新任务，等待在途事务或按任务协议收尾。
3. 放入新版本目录，先配置校验/目标核对，再单独迁移；成功后启动新应用，B worker按版本协议恢复。旧版本和数据卷保留。
4. 验证HTTPS、登录/保存/回读、隔离、关键账目、任务/备份，记录结果再开放；失败保持维护并按兼容策略回退或前滚。

命令按已验收README及第7节的真实发布包执行；不能把 `git pull` 后现场装依赖、自动补列当完整发布。普通更新不切PostgreSQL大版本、不随手更换数据卷目标、不拉取浮动`latest`。

### 13.2 停服务与删数据的区别

在Compose中停止/重建应用容器不应删除持久卷；但更换项目名、卷名或挂载路径可能连到一个新空库，看起来像“数据丢失”。交付必须固定Compose项目身份/卷名并记录实际卷，跨release路径也保持一致；若遇空库先核对挂载，不初始化覆盖旧卷。

**`docker compose down -v` 会涉及删除卷，禁止作为常规更新/排障命令。** 本指南不提供删除数据库、删除备份或清理真实卷的命令。需要释放资源时先列出确切目标、依赖、可恢复副本和影响，再获具体删除授权。

### 13.3 回退选择

| 情况 | 可用路径 | 必须说明 |
|---|---|---|
| 新应用错误，schema仍兼容旧版 | 停写/暂停worker→切回已验收旧镜像/配置→健康与账目检查 | 新字段/任务状态是否旧版能读，不能简单假定 |
| 迁移已提交且旧版不兼容 | 优先前滚修复；或按演练恢复完整数据库及配套应用 | 无损downgrade未证明就不执行；停写并保留失败库 |
| 原机损坏 | 独立副本恢复到新机/新库→权限/主密钥/应用→核账→DNS切换 | RPO损失窗口及实际恢复耗时；DNS缓存可能延迟 |
| 切云后想回本地 | 先停云写入并保留新增数据，制定导出/导入/补录方案 | 冻结旧SQLite不包含上线后的新事实，不能静默覆盖 |

**成功标志：**回退后可读写、账目/权限一致、最新备份任务恢复，用户知道实际损失窗口。  
**失败处理：**继续维护、保存证据和所有副本，邀请实施者在隔离环境排查，不用删除/重算把问题隐藏。  
**下一步：**更新操作记录和开发问题清单，解决后再放开邀请。
