## 3. 第一批：三个必须修复的问题

### R01 / P1：切换供应商必须重新绑定密钥

**位置：**`app/services/credentials.py:60–84` 的 `save_config`；`frontend/src/components/SettingsView.vue` 的供应商选择、配置加载和保存。

**复现与影响：**先保存 DeepSeek 的合成 Key，再选择 SiliconFlow 并省略 `api_key`。后端更新 `provider_id` 却保留旧密文，解析出的请求目标变化而 Key 没变。前端“已配置”状态未随着供应商改变清除，能够提交这种输入。下次调用可能把 A 供应商 Key 发给 B。

**要求：**

1. 后端比较保存前后的供应商。供应商变化且仍要启用调用时，必须提供新 Key；省略字段和 `__KEEP__` 都不得跨供应商继承。清空或停用可以保留为显式操作，但停用状态也不能悄悄把旧密文重新解释为新供应商密钥。
2. 只修改同一供应商的模型时，允许按现有协议保留 Key；保留、替换、清空分别测试。无效输入完整回滚，不能留下新供应商配旧密文的半更新状态。
3. 前端切换供应商后显示“需要重新填写此供应商的 Key”，掩码不能当真实 Key 提交；primary 和 aux 两组同样适用。后端校验不能依赖前端。
4. 合法配置变化递增版本，运行中的旧任务禁止迟到写回；已有错误组合不能仅靠升级自动判断 Key 属于谁，提供不泄密的重新绑定提示/处置说明。
5. 保持明文不入日志、URL、导出和异常信息；API 配置回读只给现有受控掩码及状态。

**验收：**A→B 不带新 Key、带 `__KEEP__` 均拒绝且数据库不变；带 B Key 成功；同供应商换模型保留 Key；清空后不再调用；双账号互不影响；换 Key/供应商期间旧分析结果失效。用替身拦截实际发出请求，断言目标与凭据匹配，不使用真实 Key。对应 T13/T14/T19。

### R02 / P1：兑换的一次操作在重试时必须保留同一个请求号

**位置：**`frontend/src/api.js:198` 的 `redeemShopItem`；`frontend/src/components/ChallengeView.vue:403–419` 的 `redeem`；`app/routers/shop.py` 兑换回执链。

**复现与影响：**前端每次调用内部执行 `crypto.randomUUID()`。80 币兑换 10 币物品后，服务端已提交而响应丢失，或者成功后的列表刷新失败；用户重试会带新 UUID。直接路由内存验证：同 UUID 重试仍为 70 币、同一兑换；新 UUID 使用相同物品版本会变为 60 币、两条兑换。

**要求：**

1. 由业务操作生命周期创建 UUID，API 包装函数接收该 UUID，不在每次传输重试时重建。保留原始 payload、物品 ID 和 expected_version；重试不能偷偷换版本或正文。
2. 未决兑换状态至少覆盖请求发出、响应未知、页面刷新后恢复。按账号隔离保存，只保存恢复必需信息；账号退出及切换按既有隐私约束处理。存储失败时给明确可恢复处理，不能声称已可靠保留重试状态。
3. 已提交但响应未知时，只允许查询回执或携同一 UUID 重试；不能把网络错误解释为“未扣币”，也不能通过清除未决状态自动生成第二笔。
4. 将“兑换成功”与“刷新列表失败”分开。已经获得成功回执后，即使 loadShop/loadCoins 失败，也显示已兑换，并提供刷新入口。
5. 用户明确发起第二次兑换才生成新 UUID；允许正常多次兑换，不用物品级永久去重掩盖问题。
6. 回执与兑换、扣币继续同事务；回执查询/恢复路径校验当前用户和操作归属，不能泄漏另一账号结果。

**验收：**POST 提交后丢响应、成功后 GET 失败、双击、刷新、账号切换、同 UUID 异正文 409；每次逻辑兑换只有一张券和一笔扣币。明确新发起的第二次兑换仍能成功。至少包含一个真正经过前端调用链的测试，不以仅测后端同 UUID 代替。对应 T05/T06/T10。

- 在空预发库上观察至少 30 分钟，覆盖双账号文字保存、列表/搜索、图表、单 worker 分析替身、报告和一次备份。记录每类操作的时间段、容器峰值、主机可用内存、换页和退出情况；真实供应商只在单独授权后少量验证。
- 本轮建议验收阈值：常规测试段可用内存大部分时间不少于 256MiB，零 OOM/异常重启，Swap 不持续增长且无持续明显换页，保存/回读没有超时或丢失。它是预发判定建议，不是当前性能结论或服务承诺；若调整必须给实测理由。
- 不足时先定位构建峰值、异常驻留、数据库/连接配置及并发，给出可验证调整；确实不足再向用户报告升级理由。不能只降低容器上限直到进程被杀。
- 临时备份/迁移进程纳入峰值预算；首次部署与备份增长不能挤满根分区。日志轮转和磁盘告警实际生效。

### R10：远端备份、暂存清理与告警（A09，T17）

1. 保持同一 PG 快照的 dump/manifest、一致行数/哈希、备份校验和、迁移头与凭据解密检查；按已有计划远端保留 7 个日备份、4 个周备份。
2. 添加受控暂存清理：仅处理指定备份根目录、明确生成规则和满足保留条件的文件；校验解析后绝对路径并拒绝越界/符号链接绕过。失败上传不能删除唯一可用副本；远端成功与恢复验收状态必须可区分，至少保留最近一个已验证本地包。不得无差别清理目录。
3. 补齐服务不可达、worker 停滞、备份失败/过期和磁盘不足告警。采用轻量、可配置方式；外部不可达检测不能只放在被监控的同一服务器。提供脱敏替身测试；真实通知目标由用户配置并授权验收。
4. 备份失败必须非零退出，不能刷新“最近成功时间”；演练远端拒绝、口令错误、校验不符、磁盘不足、告警发送失败，不输出秘密。
5. 异机恢复从独立远端仓库取回，主密钥从单独离线副本取回；只写新的隔离目标库，已有库名拒绝，不能覆盖生产。实际登录、回读、核账和测试凭据解密。
6. 记录备份生成/上传时点、恢复开始/结束、数据范围和版本。延续目标 RPO≤24 小时、RTO≤4 小时；这是需要演练证明的目标，不是已经成立的 SLA。同宿主机的新 schema/新数据库不能充当异机验收。
