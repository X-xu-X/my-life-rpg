## 阶段 0：需求澄清（把模糊想法变成可执行需求）

**真实案例**：最初只有一句话——"我想制作一个联网的网页或 app，把锻炼学习等事件输入后，大模型科学判断加技能点"。通过 10 轮单问题追问（用户定位→记录方式→属性体系→判定控制权→产品形态→技术栈→部署→游戏化深度→扣分机制→合规），逐层锁死边界；再扫描 GitHub（Habitica 14k star GPL-3.0 / 两个 0-star 小项目），用"License 不兼容 + 核心差异点开源界没有 + Fork 等于重写"三条理由定下**自研**。

### 🤖 AI 辅助开发线
- **追问式访谈法**：让 AI 一次只问一个最关键的问题，按"用户→功能边界→技术→合规"的顺序逐层深入，直到对齐（可复用 prompt 模板见本阶段经验）。
- **开源调研决策法**：扫描关键词 → 用 GitHub API 核实 Star/License/活跃度 → 按"复用 / Fork 改造 / 自研"三选一并给出不可辩驳的理由。关键判断点：License（GPL 传染性）与技术栈是否匹配、灵魂功能是否已有实现。
- **关键经验**：AI 给建议时要它"先给结论再给理由"，且理由必须是可证伪的事实（License 条款、Star 数），不是感觉。

### 🛠 传统开发线
- **需求工程基础**：功能边界（要什么/不要什么）、非功能需求（隐私、成本、口径一致性）、MVP 思维（先跑通核心闭环再扩展）。
- **竞品分析基本功**：看 Star 数不如看 License 和"它是否实现了你的核心差异点"。

### ✅ 掌握检验
- [ ] 能独立写出 10 个"一次一个问题"的访谈 prompt，覆盖一个新项目的全部关键分叉
- [ ] 给任意一个开源项目，能在 10 分钟内判断"能否复用"（License + 技术栈 + 功能匹配三条）
- [ ] 能把一段模糊描述整理成带编号的需求确认清单（像 PRD 〇 节那样的表格）

## 阶段 1：方案设计与文档化（PRD 是唯一的真相来源）

**真实案例**：需求澄清后一次性输出完整方案（需求确认清单 → 开源调研 → 结论 → 技术方案 → 数据模型 → 核心流程 → 量化锚点库 → 里程碑），落成 `docs/PRD.md`；用户补充两个关键决策（**模型固定 DeepSeek 保证口径一致**、**初始属性由 AI 问卷生成**）后再更新 PRD 版本号。后续所有开发争议都回到 PRD 找答案。

### 🤖 AI 辅助开发线
- **让 AI 写 PRD 的正确姿势**：把访谈结论结构化喂给它，要求"分节输出 + 每节可独立修订 + 带版本号"；用户口头补充的决策必须**当场写进文档**而不是留在聊天记录里。
- **给执行 AI 写任务书（WRITER_PROMPT）**：技术栈约束（不可更改区）+ 核心闭环（验收视角描述）+ 数据模型 + Git 工作流铁律 + 交付顺序 + "与 PRD 冲突时保守实现，不确定写 TODO 进 DECISIONS.md"。这是本项目最成功的一份文档——Writer 从未跑偏。
- **DEV_PLAN 批次计划**（v1.3 首创）：大改动拆成 P0/P1/P2 批次，每项给"背景根因 → 需求 → 文件级技术方案 → 验收标准"，批次间强制自验。Writer 一轮就完成了全部三批次零返工。

### 🛠 传统开发线
- **PRD 结构学**：需求清单表、用户故事/流程图、数据模型（ER）、API 设计、非功能需求、里程碑。学到能看懂并手改任意一份 PRD。
- **技术选型论证**：本项目"Python 全栈"三理由（AI 生态/个人熟悉/演进平滑）是标准论证格式——每条理由都可被事实检验。
- **量化锚点库设计**（本项目独有的好设计）：把"AI 凭感觉打分"变成"AI 在标准基准上加权"——为 AI 输出建立**事实基准表**（如 30min 有氧=体能+1，附 ACSM 依据），这是所有"AI 判定类"产品的通用解法。

### ✅ 掌握检验
- [ ] 能不借助 AI 手写一份 5 节以上的迷你 PRD（含数据模型草图）
- [ ] 能给一个新项目写出 WRITER_PROMPT 级别的任务书（含 Git 铁律与验收标准）
- [ ] 能说清"锚点库"解决了 LLM 打分的什么问题（口径漂移 vs 有据可依）

## 阶段 2：工程基建（仓库、规范、一键启动）

**真实案例**：git init + 局部身份配置（`X-xu-X <1968720131@qq.com>`，不污染全局）→ .gitignore（.env/数据库/缓存/工具目录）→ .env.example 模板（占位符不含真密钥）→ GitHub 私有仓库（gh CLI 设备码授权）→ start.bat/start.sh 一键启动（装依赖→起前后端→探测 /api/health→开浏览器）。

### 🤖 AI 辅助开发线
- **AI 代替你跑环境命令**：winget 装软件、gh 授权、git 配置——全部可以让 AI 执行，你只需要**批准 + 在浏览器完成必须本人的授权步骤**。
- **一键启动是 AI 协作项目的刚需**：每个里程碑交付后强制要求 start.bat 可用——否则每次测试都要手动三步，反馈周期拉长一倍。

### 🛠 传统开发线
- **Git 核心工作流**（本项目用到的全部）：init/config 局部身份/add/commit -m（中文规范 message：`类型: 简述`）/log/status/branch -m/remote add；理解"本地 commit ≠ push"——**push 时机永远由人掌控**，这是 AI 协作的安全边界。
- **commit 粒度即文档粒度**（v1.4~v1.7 实践出的节奏）：一个版本的提交序列固定为 —— `docs: 开发计划 vX` → `feat(A1)...` `feat(B1)...` `fix(A5)...`（**按批次拆，一个批次一个 commit**）→ `docs: 回写 vX 完成状态`。**回读验证**：AI 执行 commit 后**必须 `git log` 回读确认**——本项目发生过"以为 commit 了其实没执行、HEAD 停在旧提交"的坑（v1.7 时踩到，靠回读发现并补执行）。
- **密钥管理铁律**：.env 进 .gitignore、.env.example 只放占位符、任何密钥不入提交。违例一次，密钥作废一次。**扩展（v1.4 BYOK）**：用户自带密钥入 `settings` 表时，**接口层必须掩码回显**（只给 `sk-****末4位`），保存时用 `__KEEP__` 哨兵值表示"不覆盖"——密钥的全生命周期都不该以明文形式在浏览器与服务器之间往返。
- **CORS 与本地开发**：前端 5173 调后端 8000 需要 CORSMiddleware；V1 本地放宽 `allow_origins=["*"]`，上云必须收紧——记住"放宽有场景，收紧有时限"。

- [ ] 能 5 分钟内为一个新项目手工配齐 .gitignore + .env.example + 首次提交
- [ ] 能解释为什么 .env.example 里的 key 必须是假值（git 历史永久保留）

## 阶段 3：MVP 开发与验收（M1）

**真实案例**：Writer 按 WRITER_PROMPT 交付 M1（FastAPI 骨架 + 10 张表 + 打卡 + 判定闭环 + Onboarding + 属性面板，8 个 feat 提交）。用户实测提出 6 条反馈，其中一类是**功能缺失**（误提交只能反驳不能删、AI 判定没有分析过程），一类是**架构预留**（登录系统属于 M4、BYOK 属于 M4）——AI 帮忙做了归类：前者立即修，后者不是 bug 是排期。

### 🤖 AI 辅助开发线
- **验收三板斧**（让 AI 执行，你看结果）：①语法/构建检查（py_compile + npm run build）②隔离环境冒烟（临时 venv + 临时 DB + curl 打一遍核心接口）③**数据层验证**（对关键业务规则写一次性脚本验证，如"入账后删除事件，点数是否回到原值"）。
- **反馈分类学**（M1 实测反馈的处理框架）：是 bug 还是缺功能？属于当前里程碑还是未来排期？——**不是所有"没实现"都是缺陷**，先对照 PRD 里程碑划分再定处置。
- **AI 改代码后的验证清单**：模型/SQL/prompt/服务/路由/前端逐层检查是否同步改了（如加 analysis 字段要动 models + schema.sql + prompt 输出格式 + 服务层存取 + 路由返回 + 前端展示，六处联动）。改完让 AI 跑全链路冒烟，并检查数据库迁移问题（SQLite 已有表不会自动加列——后来专门写了 migrate_schema 轻量迁移解决）。

### 🛠 传统开发线
- **分层架构读写**：路由层（参数校验/HTTP 语义）→ 服务层（业务逻辑）→ 模型层（ORM）→ 数据库。判断一段代码放哪一层的依据：换 UI 要不要重写？（不用→服务层）换数据库要不要重写？（不用→模型无关）。
- **审计流水设计**：任何改账本的操作（加分/回滚）都写一条 append-only 流水（delta + value_after + reason + evidence），出错可对账。这是金融级习惯，通用。
- **HTTP 状态码语义**：400 参数/业务拒绝、404 不存在、409 冲突（重复确认）、503 依赖（LLM）不可用。

### ✅ 掌握检验
- [ ] 能照着"验收三板斧"独立验收 Writer 的一次交付，并给出 PASS/FAIL 结论
- [ ] 拿到一条新反馈，能按"bug/缺功能/排期项"归类并说出依据
- [ ] 能解释 attribute_history 为什么设计成 append-only 流水而不是只存当前值

## 阶段 4：迭代与反馈闭环（M2/M3 → v1.1~v1.10，本项目的精华）

> 这一段是全项目最有价值的部分。**从 v1.1 到 v1.10 的完整迭代**，每个版本都遵循同一套四拍节奏：**backlog 登记（带数据诊断）→ DEV_PLAN 批次计划 → 分批实现并逐个 commit → 回写完成状态**。下面按版本给出案例，注意每个案例的"诊断 → 决策 → 落地"链条。

**真实案例串**：

**① 判定科学性六连改（09-01~09-03，v1.1~v1.2 期间）**：累积效应（近 30 天频率注入）→ 置信度加权（delta×confidence，前端透明展示"建议+1·90%→入账+0.9"）→ 低置信度拦截（<80% 禁止入账）→ 负面行为锚点 12 条 → 边际递减（注入当前属性值）→ 不实甄别 + 诚信维度。

**② 追问失效诊断（09-05，v1.3 批次 A）**：用户反馈"AI 从不提问"。AI 先只读查询本地 SQLite 全部 9 条历史判定，发现 `needs_clarify` 无一为 true、conf 全在 0.8~0.95 → 定位 prompt 三处根因（免问出口条款 / 默认 false / 与"降 confidence"条款冲突）→ 写进 backlog → 次日成 DEV_PLAN 批次 A，Writer 一轮修复零返工。

**③ v1.4：从"能用"到"可控"（09-06~09-08）** —— 四条并行改进，全部来自实测反馈：
- **BYOK 双模型组（本次最重要的架构升级）**：用户提出"想自己配 Key"。设计上不是简单加个输入框，而是抽象出**用途 → 配置组**的解析层（`llm_config.py`）：`judge`（判定，要质量）与 `aux`（辅助任务，可省钱）**双槽位**，缺失时按 `aux→primary→.env` / `primary→aux→.env` 回退——判定的回退要**显式标注降级**（`quality_note`），辅助的回退静默。密钥存储用**掩码回显 + `__KEEP__` 占位**（前端拿到的是 `sk-****末4位`，保存时传 `__KEEP__` 表示不覆盖），避免密钥在前后端来回明文传输。**可迁移经验**：凡是"用户自带凭据"的功能，都要单独设计**读-显-存三态**（永远不回显全文 / 保存时不覆盖旧值 / 检测到模型变更要提示上下文不兼容）。
- **追问逐面 + 来源区分**：追问从"要不要问"细化为"**按生活面清单逐面问**"（覆盖自检）；同时要求 AI 在判定中区分**主动提及**与**引导后想起**的内容（后者的加点应更保守）——这是"防 AI 把追问套出来的信息当主动性证据"。
- **置信度原因（`confidence_reason`）**：置信度低于 0.95 时**强制填写理由**。这解决的是"AI 给 0.7 分但不知道为什么"——**让模型为不确定性负责**，是可信度设计的通用手法。
- **前端反馈就近化**：错误提示从顶部全局条改为挂在对应卡片上；`actionError` 与后续 v1.6 的 `actionSuccess` 都是同一思路的延续。

**④ v1.5：一次教科书级的根因诊断（09-08~09-09）** —— 用户实测报"重判后数据不对劲、审计记录对不上"。AI 没有直接改代码，而是**先读 `judge_service.py` 比对两条链路**，发现根因：**"重判"与"补充/反驳"走了两套不同实现**——`judge_event` 重判时是**删旧判定建新判定**，而 `supplement`/`dispute` 是**原地更新**。删旧建新带来三个连锁伤害：① **审计断裂**（删掉了 create 之后的日志，历史消失）② **judgment id 漂移**（前端 sessionStorage 存的 id 失效，出现"预览的是旧判定"）③ **维度漂移**（前后两次判定输出的维度集合不一致，用户看到点数莫名变动）。修复方案是**统一链路：重判一律就地更新，id 不变，审计只增不删**（`476b714` → `bc4929f`）。这一条直接催生了 v1.5 的 A1 与 v1.6 的"增量修订契约"。
- 同版本还修了另外两个 P0/P1：**A3 单一数据源**（EventForm 的预览恢复不再从 sessionStorage 读判定快照，只存 `judgmentId` 再从 DB 拉**现行**判定——彻底消灭"前端缓存与 DB 不一致"这一类 bug）；**A5 `chat_json` 自动重试**（空返回/解析失败重试 1 次，指数退避 ~1s）；**B2 输出前维度硬校验**（把"漏判维度"的兜底从 prompt 建议升级为 prompt 中的硬性校验步骤 + 服务层过滤）。

**⑤ v1.6：把"重判"做成有契约的增量修订（09-11）** —— v1.5 统一了链路但没解决**语义**问题：重判后如果 AI 只关注新增信息，会把上次已判定的维度"忘记"或"改口"。方案是引入 **`revision_notes` 契约**：重判时把上一次的判定作为**基准快照**（`_prior_snapshot`）注入 prompt，要求 AI **逐条说明每个维度是保留、调整还是撤销，撤销必须给出依据**；不相干的维度**逐字保留原文**。同时：
- **保留式成功反馈**：`runAction` 成功不再清空输入框，而是显示"操作成功"并**保留用户输入**（失败也保留，只换错误文案）——"用户的劳动成果不该因为一次成功就消失"。
- **列表日期分组折叠**：判定中心与手账本都按 今天/昨天/本周更早/更早 四组折叠，且把分组逻辑**抽成 composable**（`useDateGroups.js`）供两处复用，而非复制粘贴。

**⑥ v1.7~v1.10：从"记录工具"到"成长游戏"（09-20~09-30，四个版本一路走来）**
- **v1.7 打卡项目体系**：用户提出**事件/日记形态重构**——自建清单 + 四类性质（规划内/可选/负面/其他）、
  内容化录入替代固定参数、同日同件事自动合并、跨来源合并。做法值得留意：用户明确说"先记 backlog，
  不明确的地方之后再看" → AI 用**多轮单问题访谈**（含选项卡）逐个澄清边界，直到确认"完全掌握想法"才写 DEV_PLAN。
  **这是阶段 0 的追问式访谈法在迭代期的复用**——同一方法在项目开头与版本演进期都适用。
- **v1.8 游戏化经济系统**：AI 定制挑战 + 押金结算 + 金币体系 + 现实奖励商店 + 停滞问询 + 段位。
  这一版开始出现**"经济系统必须自洽"**的工程约束（金币唯一写入口、账目自洽校验）。
- **v1.9 体验打磨**：启动资金按问卷浮动、挑战一卡多档、**全站交互反馈规范**（toast + 就地面板）、
  手账本搜索重构、挑战来源徽章。这一版的价值在于**把"体验细节"也纳入版本范围**，而非只做功能。
- **v1.10 四项大改**（P0/P1/P2 三批）：经济定价**从写死参数表改为 AI 主导定价**（行情快照统一口径）、
  成就系统（累计型自动 + AI 发现型追授）、豁免券（时段券 + AI 判动机浮动定价）、
  属性满级拆子维度（AI 提议 + 用户多选确认）、三页合并「今日盘点」+ 可视化重做。
  **方法论意义**：一个功能上线后**推翻了它自己的初始设计**（v1.8 的写死定价表 → v1.10 的 AI 定价），
  这是"先用最简单方案验证、再按实测反馈升级"的正常路径——**不要一开始就设计终极方案**。
  **验收方式也在升级**：从"跑接口"到"真实 LLM 端到端 + 浏览器自动化（真实点按钮、像素级断言）+ 前后截图对比"。

### 🤖 AI 辅助开发线
- **数据诊断先于猜测**：用户说"维度少"，不要直接改 prompt——先查库拿证据（9 条判定实际 1~6 维），区分"用户描述少"还是"AI 漏判"，backlog 里记的结论才可信。**用 SQL 证据说话是 AI 协作里最值钱的习惯**。
- **backlog 即产品记忆**：DECISIONS.md 按"日期 + 用户反馈"分节，条目格式 `[ ] 标题：现象 + 根因 + 改进方向`，修复后改 `[x]` 附实现摘要。已否决的想法也留档（排行榜被否的三条理由），防止未来重复讨论。
- **prompt 调优方法论**（从追问失效案例提炼）：①找到给模型留的"逃逸出口"（如"没意义就不问"）②检查输出模板的默认值倾向 ③检查条款之间是否互相矛盾 ④修改后用真实数据回归验证，不凭感觉。
- **多实现路径的一致性审查**（v1.5 最值钱的教训）：**当一个功能有多条入口时，先问"它们是不是走了同一段代码"**。"重判"与"补充/反驳"在用户眼里是同一个动作的两个入口，在代码里却是两套分支——这类"语义同构、实现异构"的地方是 bug 高发区。审查话术：*"这个操作有几个入口？各自的代码路径一样吗？产生的副作用（审计、id、缓存）一样吗？"*
- **契约化改造**（v1.6 的方法论）：当 AI 的输出需要**跨多次调用保持一致**时，不要指望它记住——把上一次的结果作为**显式基准**注入，并要求它**逐条声明处置方式（保留/调整/撤销+依据）**。这就是"增量修订契约"，适用于任何"多轮改写同一对象"的场景（文档润色、配置生成、代码重构）。
- **里程碑制自评**：每阶段开工前确认范围、AI 自评 >95% 把握才动手——把"AI 幻觉风险"压在开工前而不是返工时。

### 🛠 传统开发线
- **调试方法论**：复现 → 缩小范围（前端刷新时机？后端漏写？）→ 查证据（读代码/查数据）→ 修复 → 回归。本项目"审计轨迹"问题就是标准案例：先查后端写入点（齐全）再查前端（找到根因）。
- **故障档案制**（2026-09-22 建立）：**每次修复 bug 都要留五栏档**（现象 → 定位过程 → 根因 → 修复实现 → 防复发）。档案存在 `CODE_GUIDE.md` 第 11 章，当前 **14 条**。
  - **为什么不只写"改了什么"**：只记改动，三个月后你只看到 `fix(A4): 修复两个链路 bug`，不知道是哪两个、为什么会有、下次怎么避免。**"定位过程"比"修复结果"更有教学价值**——它教你怎么查，而不只是改了什么。
  - **建档时机是硬约束**：必须**当时就记**。事后补写会丢失证据细节（试过什么、排除了什么），而那些恰恰是最有价值的部分。
  - **14 条的分布本身就是一份 checklist**：规则/prompt 边界不清 4 条、多入口不同步 2 条、写库语义错误 1 条、外部依赖无容错 1 条、模型输出格式假设 2 条、迁移不完整 2 条、辅助阻断主流程 1 条、幂等缺失 1 条。**新项目的同类风险点可以直接照这张表排查**。
- **前端状态管理**：内存 ref 切页即丢 → localStorage（持久草稿）vs sessionStorage（会话级结果）的选型依据；Vue 的 `watch` + `deep` 实现自动持久化。**进阶（v1.5 A3）**：sessionStorage 里**只存 id 不存数据快照**，是"单一数据源"原则在前端的最小落地——**缓存只缓存指针，不缓存副本**。
- **前端组件复用**：Vue3 **composable**（`useDateGroups.js`）是"无 UI 的逻辑复用"——两处列表需要同样的日期分组，抽成 composable 比抽成组件更轻（不需要模板、不需要 props/emit 协议）。判断标准：**复用的是逻辑还是外观？逻辑→composable，外观→组件**。
- **防重复/幂等思维**：判定幂等（confirmed 拒绝重判、pending 就地更新）、锚点种子幂等写入、迁移幂等——**幂等是一切自动化操作的安全垫**。
- **凭据管理的读-显-存三态**（v1.4 BYOK）：掩码回显、`__KEEP__` 不覆盖、变更检测——任何"用户自带密钥"的功能都要走这套。

## 阶段 5：稳定运营（数据主权与运维）

**真实案例**：启动自动备份（SQLite backup API 在线复制，保留 30 份）+ 手动备份入口；数据导出 JSON/CSV（CSV 加 BOM 防 Excel 乱码）；重置角色档案（解锁 Onboarding 不清数据）与重置全部数据（二次确认）双档位；维度三态开关（显示/隐藏/关闭判定，重开不校准从冻结值继续）。

**运行时韧性（v1.4/v1.5 补强，属"运营期才知道需要"的一类）**：
- **LLM 调用重试**（v1.5 A5）：`chat_json` 空返回或解析失败**自动重试 1 次**（指数退避 ~1s）。**为什么值得单独做**：运营期最大的体验杀手不是"判定不准"，而是"偶发失败让你白填一遍表单"——一次透明重试能吃掉绝大部分瞬时抖动。**设计边界**：只重试 1 次（成本可控），且只对"空/解析失败"重试，不对业务性失败重试。
- **降级可感知**（v1.4）：BYOK 缺失时判定回退到辅助模型，此时 `quality_note="判定质量一般（使用辅助模型）"` 会一路传到前端展示。**降级服务可以，但必须让用户知道自己在用降级服务**——静默降级是对信任的透支。
- **失败不丢输入**（v1.6）：操作失败或成功都**保留用户输入**，只替换提示文案。这条来自实测反馈"点了确认，成功提示一闪，我填的东西没了"。
- **备份清理失败的静默处理**（v1.1 期）：`6dd6c8e` 让清理旧备份失败时**不影响启动**——"辅助功能不得阻断主流程"是运维设计的一条通则。

### 🤖 AI 辅助开发线
- **让 AI 设计"档位"**：危险操作永远问 AI"这个操作有哪几档？误触代价是什么？"——AI 会给出重置档案/重置数据/删除单条的多档设计，比你直接说"加个删除"结果好。
- **备份验证**：让 AI 定期验证备份可用性（列出文件+大小），而不是备份完就忘。
- **韧性清单**（让 AI 审视每个外部依赖）：超时了吗？重试了吗？重试几次？失败降级了吗？降级被用户看见了吗？失败后用户的输入还在吗？——这六问能覆盖绝大多数"偶发但烦人"的线上问题。

### 🛠 传统开发线
- **SQLite 运维常识**：backup API vs 直接复制文件（后者可能拷到半写状态）；`check_same_thread=False` 的原因；单文件数据库的备份/迁移优势。
- **用户数据导出义务**：JSON 全量 + CSV 常用子集两种格式；字符编码坑（BOM）。
- **重试与退避**：什么时候该重试（瞬时故障、幂等操作）、什么时候不该（业务拒绝、非幂等写）、退避为什么用指数——这是分布式系统的入门课，单机项目同样适用。

> **迭代期的一句话补充（v1.4~v1.7 提炼）**：**多入口先查一致性，AI 输出先问它敢不敢为不确定性签字，多轮改写先立契约。**
