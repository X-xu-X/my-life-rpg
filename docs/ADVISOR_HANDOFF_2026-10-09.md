## 二、产品背景与用户目标

项目名：游戏人生 / Game of Life。现有系统通过记录生活事件、AI 分析与用户确认，驱动属性变化，并已有目标、挑战、金币、商店、成就、豁免等功能。

本次重新访谈后，用户最看重的是：

1. 获得生活的意义感，愿意持续做提升自己的事情。
2. 留下生活记录，日后可以回看和纪念。

使用对象依次为本人、身边有需要的朋友、未来公众用户。希望项目成为面试技术亮点，并探索适度商业化。现在优先解决自己的真实使用需求和朋友反馈渠道，收费不是首批目标。

建议定位：用轻松的记录与回顾，把生活中的行动、变化和意义积累成可看见的成长。

## 五、开发文档的范围与推荐顺序

### 阶段 A：手机文字内测与上云基础

目标：项目所有者关掉电脑，自己和朋友仍能从手机链接独立使用。

需要设计的内容：

- 邀请与登录、统一当前用户上下文、账号初始化。
- 全部数据与操作归属隔离，包括按 ID 访问、修改、删除、导出、设置、记忆、任务及金币结算。
- 自带 Key 的绑定、测试、掩码回显、加密保存、替换与失效处理。
- 限制用户提供的模型地址访问内网、云元数据等非预期目的地。
- 最小可用的手机布局：保存、回看、确认、补充、复核与错误反馈。
- 无模型 Key、模型不可用时仍能保存和回看文字。不得为了快速记录强制用户先完成长问卷；需兼容现有建档完成判据。
- 生产构建、同域 HTTPS、进程托管、数据库持久化、独立备份与恢复、基本日志和用量限制。
- SQLite 到目标数据库的迁移与真实数据归属安排。

请评估同机 PostgreSQL 的实施与运维代价；若建议暂时保留 SQLite，需明确写并发约束、部署形态和迁移触发条件。默认推荐 PostgreSQL，但禁止假定现有业务已经兼容。

### 阶段 B：轻松记录与睡前回顾

目标：白天不被分析流程打断，晚上能集中整理，任何一次失败都不会丢掉已保存内容。

- 记录保存与分析分开，原始文字不被 AI 覆盖。
- 立即分析、稍后处理、不分析三种意图能表达清楚。
- 追问可延期回答，待确认内容有统一入口。
- 日记回顾复用当天已有记录，不重复创建同一件事和发放奖励。
- 草稿与待处理状态在合理范围内持久化；登出、换账号时不串数据。
- 需要后台继续执行的任务必须持久化，设计超时、租约、有限重试、记录版本校验和幂等。
- 初期避免为任务处理新增昂贵基础设施；可评估数据库任务表与同机 worker。

推荐状态表达应将“保存成功”和“分析完成”分开。若先交付简单人工触发，再加入后台任务，请清楚说明能力边界，不得把进程内临时任务描述成可重启恢复。

### 阶段 C：成长表达与 UI 完整改造

用户已赞成“成长经验与当前状态分开”。请设计如何在不破坏既有数据的前提下逐步上线，不要求为了首批手机内测一次性重做全部经济系统。

需说明：

- 哪些指标表示已完成行动的积累，哪些表示实际表现，哪些来自用户感受。
- 生病、状态低落、未记录、未行动之间的区别。
- 原有 13 维属性、初始快照与历史流水如何保留和解释。
- 新规则从何时开始，如何记录版本，如何与旧面板并存或过渡。
- 酌情减免如何说明依据、限制调整范围、允许纠正；处境记忆如何过期。
- 不凭完成任务推断幸福感上涨，不将游戏点数承诺为经过科学验证的精确能力测量。
- 状态未知、信息不足和长期未更新时如何展示。

UI 可以与阶段 A/B 同步做必要部分，完整视觉统一放在这一阶段。顾问应明确依赖，避免重复改同一页面。

- 云账号、必要认证、预算和续费提醒。
- 域名候选、域名归属及解析权限。
- 仓库与部署方式、代码版本、运行时与依赖清单。
- 现有真实数据的备份，以及是否迁入云端首个账号的确认。
- 用户自己管理的模型配置；演示与测试使用虚构数据。
- 服务器登录凭据、应用加密密钥、数据库凭据如何生成与保管。

不要要求项目所有者把云主账号密码、API Key、数据库密码或 SSH 私钥粘贴到聊天或文档。指南用占位符示例，说明该填在哪里、如何确认已配置、怎样更换。

### 7.4 按顺序写完整操作流程

建议按下面阶段展开成可照做的说明：

| 顺序 | 事项 | 指南需要给出的判断标准 |
|---|---|---|
| 1 | 确认地域、套餐、域名和费用 | 有具体订单项和续费信息，知道哪些先不买 |
| 2 | 完成开发并在隔离环境验收 | 有可部署版本、配置模板与通过记录；无需等待所有远期功能 |
| 3 | 创建服务器与基础环境 | 能安全登录、磁盘与时间正确、仅开放必要服务 |
| 4 | 部署数据库和应用 | 数据目录持久化、进程可重启、配置不入代码库，数据库不直接向公网开放 |
| 5 | 域名解析与 HTTPS | 手机外网打开正确域名，证书有效；前后端同域工作 |
| 6 | 备份与数据迁移 | 先备份；副本迁移验证；默认用户数据只归属指定本人账号，朋友账号为空 |
| 7 | 上线前功能与权限验收 | 两个独立测试账号交叉验证、模拟 AI 失败、手机完整流程和恢复演练 |
| 8 | 邀请少量朋友 | 邀请可控、反馈入口清楚、无必须付费配置以外的意外门槛 |
| 9 | 日常维护和后续更新 | 会看运行状态与费用，会备份、验证、更新、回退，并有故障时的处理步骤 |

环境应明确区分 Windows 本地与 Linux 云端，不混用命令。不要将 Vite 开发服务器或 `uvicorn --reload` 当作生产运行方式。SSH 管理端口的访问范围应单独说明，不因网站可访问就开放数据库、任务管理和内部接口。

若采用 Docker Compose，指南写明容器、网络、数据卷、版本与备份关系；停止容器、删除卷、重建数据库的效果必须区分。不要给初学者会不经意清空数据的默认更新步骤。

### 7.5 每一步都写成可核验的操作

每步采用：目的 → 入口/命令及执行位置 → 所需占位值 → 成功现象 → 常见失败 → 下一步。

命令应以最终开发产物为准；在部署脚本、镜像、配置变量尚不存在时，不编造“直接复制即可执行”的命令。可以先写操作框架，并明确哪些命令需在开发交付后补齐。

指南还需覆盖：如何查看日志但避免泄露私密正文和 Key；服务器重启后恢复；数据库备份与独立恢复；云盘空间和流量不足；模型配置失效；证书续期；更新失败的代码和数据库兼容回退。

需分别说明数据库独立备份与服务器快照，避免只在同一台机器保存唯一备份。基础配置可以先提出每日备份等候选目标，但恢复点与恢复时间应按演练结果说明，不能凭空承诺。

## 八、授权、数据与交付边界

本次授权为顾问编写文档，不包含购买、实际开通付费服务、把真实库上传云端或公开上线。执行时应先完成具体清单和验证材料，再由项目所有者确认采购或真实数据迁移等动作。

既有真实库不得物理清空或作为故障测试库。开发新增字段、改变规则或迁移数据库，都需先有副本、兼容方案和验证。自动任务不应消耗未明确授权的平台公共模型额度；每用户配置的模型费用归属应清楚。

朋友的私密正文不应默认成为顾问的测试素材。用户反馈与技术日志尽量采用操作耗时、失败类型和自愿提供的例子；演示账号使用虚构数据。

如后续由 Writer 实施，应在新工作指令中明确版本边界、允许修改的模块和验收要求；既有仓库只本地提交、不自动 push 的约定继续保留，除非项目所有者另有授权。本次交接不要求现在提交或发布代码。
