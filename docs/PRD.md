|--------|--------------------------|
| 版本 | v1.0 |

| 定位 | AI 驱动的个人成长游戏化系统 |

---

## 1. 项目概述

### 1.1 一句话定义
用户记录真实生活事件（锻炼、学习、作息等），系统接入大模型，基于科学标准判断每件事对个人能力的实际影响，换算成 RPG 式属性点增减，让"成长"变得可量化、可回溯、可激励。

### 1.2 核心价值
- **科学**：每次加点/扣点有可引用的依据，不是 AI 随口打分
- **可信**：AI 建议 → 用户确认 / 反驳 / 补信息 → 客观复核，用户对结果有完全掌控
- **激励**：属性面板、等级、成长曲线让坚持看得见

### 1.3 产品愿景
从个人自用出发，渐进演进为小圈子共享、再评估公开产品化。

## 2. 目标用户与使用场景

| 阶段 | 用户 | 核心场景 |
|------|------|----------|
| V1（当前） | 本人（个人自用） | 每天记录锻炼/学习/作息等事件，AI 判定加点，查看属性成长 |
| V2 | 小圈子（朋友） | 排行榜、互相激励，需要多用户与邀请机制 |
| V3（评估） | 公开产品 | 注册体系、运营、可能的商业化 |

**关键画像**：注重自我提升的年轻人；愿意每天花 1-2 分钟记录；对"科学依据"敏感，反感无脑打分。

---

## 3. 核心概念

- **事件（Event）**：用户记录的一条生活行为，分三类：
  - `positive` 正面事件（锻炼、学习、早睡…）
  - `negative` 负面行为（熬夜、久坐、暴饮暴食…）
  - `goal` 目标相关（目标达成 / 未达成）
- **属性（Attribute）**：能力维度，如体能、智力、情商、创造力、规划力、健康。由 AI 依据用户画像生成初始值。
- **判定（Judgment）**：AI 对一条事件的分析结果：影响哪些属性、增减多少点、科学依据、置信度。
- **量化锚点（Anchor）**：内置"标准事件基准表"，AI 判定时以此为基准按强度/时长/质量调整。

## 4. 功能需求

### 4.1 Onboarding：初始属性设定（AI 问卷制）

**流程**（用户首次使用）：

1. 用户选择"开始建立角色档案"
2. **AI 出题**：AI 动态生成一系列问题，覆盖维度：
   - 体能健康（身高体重、运动频率、体能自评、睡眠作息）
   - 学习能力（专业、学习时长、专注度自评、近期学业表现）
   - 社交情绪（社交频率、情绪稳定性、压力水平）
   - 生活管理（作息规律性、自控力自评、理财习惯）
   - 其他兴趣技能（编程、外语、乐器等）
3. **对话式作答**：用户逐题回答；AI 可根据关键回答追加追问（如"你每周跑步几次？大概多远？"）
4. **AI 生成初始面板**：回答结束，AI 输出初始属性面板，**每个属性附带推导依据**（如"体能 62/100：每周 3 次有氧 + 睡眠 7h，处于同龄人中上水平"）
5. **用户确认 / 调整**：对某属性有异议可说明理由，AI 复核后调整；确认后存档为初始快照

**交互形态**：V1 采用对话式（消息流界面），复用判定闭环的"确认/反驳"机制。

### 4.2 事件录入（双通道）

- **结构化打卡**：表单录入 —— 选事件类型 + 类别（锻炼/学习/作息/社交/饮食/理财…）+ 关键参数（时长、距离、配速、强度、是否完成…）
- **自由日记**：文本输入 —— 随便写一段话（如"昨晚 9-10 点在路边慢跑 5 公里，配速 6'50"），AI 自动解析事件要素
- 两种模式可随时切换；日记模式录入的事件由 AI 提取结构化要素后进入判定流程

### 4.3 AI 科学判定闭环（产品灵魂）

```
事件录入 → AI 解析事件要素
  → AI 判定：{受影响属性[], 各属性增减量, 科学依据, 置信度}
  → 用户三选一：
     ① 确认 → 点数入账，生成判定记录
     ② 补充信息 → 附加说明后 AI 重新判定（如"其实中途走了两次"）
     ③ 反驳 → 陈述理由，AI 依据事实复核（客观，不迎合；无据反驳维持原判）
  → 任何操作写入审计日志，全程可回溯
```

**客观性硬约束**：AI 复核用户反驳时，仅以事实和科学依据为准；若用户反驳缺乏依据，AI 应坚持原判定并说明原因，**不得一味迎合**。

### 4.4 属性与点数系统

- 初始属性：AI 依画像生成（100 分制），含依据
- 加点：AI 依据量化锚点 + 事件强度调整，单次增减建议在合理区间（如 -5 ~ +5）
- 属性历史：每次变动记录流水（时间、事件、增减量、依据），支撑趋势可视化
- **锚点库用户可见可校准**：用户可查看"为什么这个事件加这些点"，对锚点标准有异议可调整，后续判定随之校准

### 4.5 目标系统

- 用户设定目标：描述 + 指标（如"本月跑步累计 50km"）+ 期限
- 达成 → 奖励对应属性点（默认 +2 规划力 及目标关联属性）
- 到期未达成 → 扣「规划力」（默认 -1，未合理规划）
- 目标可中途修改/取消（记录审计）

### 4.6 游戏化与可视化（中度起步，重度可升级）

**V1（中度）**：
- 属性面板（数值 + 进度条）
- 人生等级 + 经验条（升级经验曲线随等级动态增长）
- 可视化：属性雷达图、成长趋势折线、月度活动热力图

**扩展模块（重度，设置中可开关，V3 交付）**：
- 成就徽章系统
- 连续打卡 Streak
- 每日/待办任务清单
- 金币自我奖励商店（如"看一集剧"作为奖励兑换）

### 4.7 设置与数据管理

- 模型配置（见第 5 节，默认固定、可插拔）
- 锚点校准入口
- 数据导出（JSON/CSV，个人数据主权）
- 游戏化模块开关

## 5. 模型策略（重要决策）

**结论：V1 规定一个模型（DeepSeek），架构可插拔，不提供"每次判定选模型"。**

理由：
1. **判定口径一致性**：同一事件由不同模型判定会得到不同加分，破坏数据可比性与可信度——"科学"的前提是口径稳定
2. **成本与生态**：DeepSeek 已有 key、成本低、OpenAI 兼容 SDK 接入简单
3. **架构解耦**：所有 LLM 调用集中在 `llm_service` 层，模型名/参数在配置文件中；未来需切换或支持多模型时，仅改配置，不动业务代码

| 配置项 | 默认值 |
|--------|--------|
| LLM provider | DeepSeek（OpenAI 兼容） |
| 模型 | deepseek-chat（可配置） |
| base_url | https://api.deepseek.com |
| temperature | 0.3（判定要求稳定低随机） |

## 6. 技术方案

### 6.1 架构

```
┌─────────────┐      REST API       ┌──────────────────────────┐
│ Vue3 前端    │ ◄────────────────► │ FastAPI 后端              │
│ + ECharts    │                    │  ├─ routers/（API 路由）  │
└─────────────┘                    │  ├─ services/             │
                                   │  │   ├─ llm_service（LLM 统一调用，可插拔）
                                   │  │   ├─ judge_service（判定闭环）
                                   │  │   └─ anchor_service（锚点校准）
                                   │  └─ models/（SQLAlchemy ORM）
                                   └────────────┬─────────────┘
                                                │
                                        SQLite（本地）
                                        → 上云后切 MySQL/PostgreSQL
```

### 6.2 技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 后端 | FastAPI + SQLAlchemy | 异步、自动 OpenAPI 文档、AI 生态好 |
| 数据库 | SQLite（本地）→ MySQL/PostgreSQL（上云） | 平滑迁移 |
| AI | DeepSeek API（openai SDK） | 统一 llm_service 封装 |
| 前端 | Vue3 + Vite + ECharts | 轻量、可视化能力强 |
| 部署 | uvicorn 本地 → Docker + Nginx/Caddy | 渐进 |

### 6.3 数据模型（核心表）

```sql
users            -- 用户（V1 单用户，预留多用户）
user_profiles    -- 基础画像 + AI 生成的初始属性快照(JSON)
attributes       -- 属性定义（名称/描述/类型）
attribute_history-- 属性值变更流水（时间/事件/增减量/依据）
events           -- 事件（类型 positive/negative/goal，来源 form/journal，参数JSON或原文）
ai_judgments     -- 判定记录（事件ID/建议增减JSON/科学依据/状态 pending|confirmed|adjusted|rejected）
judgment_logs    -- 审计日志（确认/补充/反驳/复核全过程）
goals            -- 目标（描述/指标/期限/关联属性/状态）
anchors          -- 量化锚点（标准事件/基准值/可校准）
settings         -- 配置（模型、游戏化模块开关、锚点版本）
```

### 6.4 量化锚点库（"科学"的落地）

内置标准事件基准表，AI 以此为锚点按强度/时长/质量调整：

| 标准事件 | 基准增减 |
|----------|----------|
| 30 分钟中等强度有氧（慢跑/游泳/骑行） | 体能 +1 |
| 1 小时深度专注学习（无干扰） | 智力 +1 |
| 23:00 前入睡、睡眠 7h+ | 健康 +0.5 |
| 熬夜至 02:00 | 健康 -0.5 |
| 目标达成 | 规划力 +2 + 关联属性 |
| 目标未达成 | 规划力 -1 |

- AI 在基准上按事件强度/时长/完成质量做加权调整（如配速更快、距离更长则更多）
- 依据引用运动科学（如 ACSM 运动指南）、学习科学、睡眠研究等知识锚点
- 锚点表存储于数据库，用户可校准；校准后 AI 判定随之调整

### 6.5 关键 API 设计

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/onboarding/questions | AI 生成初始问卷 |
| POST | /api/onboarding/answer | 提交回答，AI 出初始属性面板 |
| POST | /api/events | 录入事件（form/journal 两种载荷） |
| POST | /api/events/{id}/judge | 触发 AI 判定 |
| POST | /api/judgments/{id}/confirm | 确认入账 |
| POST | /api/judgments/{id}/supplement | 补充信息重判 |
| POST | /api/judgments/{id}/dispute | 反驳复核 |
| GET  | /api/attributes | 当前属性面板 |
| GET  | /api/attributes/history | 属性流水（可视化） |
| CRUD | /api/goals | 目标管理 |
| GET  | /api/anchors | 锚点库（可校准） |
| POST | /api/settings | 配置（模型/模块开关） |

## 7. 非功能需求

- **隐私**：日记数据默认本地私有；上云后明确数据归属与加密（HTTPS）
- **可追溯**：所有点数变动可回溯到"事件 + 判定记录 + 依据"
- **一致性**：判定口径稳定（固定模型、低温度、锚点库）
- **可扩展**：多用户、上云、APP 均为预留演进位，不返工

## 10. Git 工作流规范（Writer 执行）

- **仓库**：本地 `game-of-life`，远端为 GitHub 私有仓库（origin）
- **提交原则**：
  - 只提交到 `main` 分支；**不 merge、不 push**
  - 一个 commit = 一个逻辑单元（如"新增事件模型"、"实现 AI 判定接口"、"添加属性面板页面"）
  - commit message 用中文，格式：`类型: 简述`（类型：feat/fix/refactor/docs/chore）
- **不得包含**：`.env`（真实密钥）、`__pycache__`、数据库文件
- **首次提交**：本 PRD 文档 + README + .gitignore + .env.example（占位，无真实 Key）

## 11. 附录：AI 判定 Prompt 模板（初始版）

系统提示词核心要求：

```
你是「游戏人生」的科学判定引擎。用户输入一条生活事件，你需要：
1. 解析事件要素（类型、强度、时长、质量）
2. 依据内置量化锚点库，判断影响哪些属性、增减多少点（-5 ~ +5）
3. 每项增减必须给出可引用的科学依据（运动科学/学习科学/睡眠研究等）
4. 输出结构化 JSON：
   {"affected_attributes":[{"name","delta","reason","evidence"}],
    "summary","confidence"}
5. 保持客观：若用户反驳，仅依据事实复核；无据反驳则坚持原判定并说明
```
