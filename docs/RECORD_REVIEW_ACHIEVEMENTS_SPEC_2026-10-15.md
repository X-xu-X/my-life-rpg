# 事件、日记、回顾与成就：补充开发草案

日期：2026-10-15。源码基线：`ba7031e`。来源：用户本轮直接反馈 F27～F33。状态：明确目标已记录；统计日期、奖励叠加与动态成就的领取方式仍有待确认，不是立即修改应用或部署的指令。

**最新澄清优先（F33）**：保留统一“晚间日记”入口，其中分区保存“我的日记原文”“AI 引导问题＋我的回答”“AI 分析”。用户强调日记保存后仍可继续 AI 回顾，问答/分析不能直接加入日记正文，必须看得见当时的问题，才能理解回答。原型上一版“加入日记”行为已撤换；事件仍独立，不新增第三类回顾打卡/奖励。未完成仍为原卡片确认后锁定、不弹成功提示。

## 1. 用户明确的目标

- 未完成在原卡片确认后锁定、不弹补充页和成功提示；计划去掉行动领域；只在到期日出现在当天安排，总计划保留并能看到数量。详见 [计划打卡草案](PLANNED_ACTION_CHECKIN_SPEC_2026-10-15.md)。
- AI 回顾先看当日计划完成情况、事件、日记和已有回答，不重复引导相关或相似的已记录内容。去重不能只比对完全相同的字句。
- 若日记已充分写了沮丧，可以邀请回想尚未写下的轻松、支持或有希望的瞬间；想不到可跳过，不强求积极、不否认原有感受。
- 事件和日记分别保存、分别展示，晚间回顾也保留两类，不合成一种记录；各自累计记录天数与最长连续天数应可查看。
- 日记与晚间回顾合成一个入口，分区保留日记原文及辅助回顾；回答、AI 引导和分析独立保存，不直接拼入日记，不改变事件与日记分开的要求。
- 达成相应里程碑可获得成就和奖励。用户询问 AI 能否发现目录外的成就并加入；这是可行性问题，尚未明确同意取消既有领取确认或新的奖励额度。

## 3. 记录分类与展示方案

增加明确的记录类型，至少区分 event 与 diary；分类和分析状态是两件事。计划打卡的实际完成内容可关联事件；单纯未完成状态不冒充事件或日记。生活补记属于哪类的最终默认行为与可选清单一起确认。

日记是用户明确保存的日记原文。“晚间日记”保留一个用户原文编辑区，旁边/按需展开显示当天事件和计划完成情况。下面独立放“AI 辅助回顾”，每次回顾按顺序显示 AI 提问、我的回答和 AI 分析；角色及来源明确标注。用户保存日记后可继续回顾，回顾回答独立保存，**不追加到日记编辑区或其存储正文**；不再提供默认“加入日记，继续”动作。保存回答不要求再点保存日记才能留住问答。

同日再次进入继续编辑已有日记，保留版本，不每次保存都追加一篇；不自动把旧多篇日记合成一篇。问答/分析是可回看的辅助记录，而非仅有无法阅读的后台元数据；一日多轮按回顾批次/时间组织，默认展示最新一轮，历史可展开。没有回答也保留已显示的问题，并标尚未回答/已跳过。用户明确结束或刷新后仍能回看，继续同一轮不重新复制问题。

修改日记保留过去的 AI 问答、分析及其当时参考版本；不把旧分析伪装成重新分析后的新版本。不另设回顾打卡连续奖；辅助记录保存不增加日记原文篇数或天数，也不重复事件属性/金币。未来若讨论使用天数，属于另一项使用统计，本轮没有新增第三类奖励授权。

旧 source 字段有输入来源语义，不能简单改成新的 record_kind：旧 journal 可能实为单事件，旧回顾也不是 diary Event。迁移保留旧来源和原文，旧记录分类策略单独确认；不擅自重写旧成就、余额或审计。日记与事件允许提及同一行动，原文分别保留；行动判定与奖励仍识别同一事实，不能一篇日记复述跑步就再奖一次跑步。

## 4. 天数口径与待确认项

事件、日记两个分类各自计算：累计不同记录日期数、当前连续天数、历史最长连续天数。同一类一天记 10 条只增加一天；同一天既有事件又有日记，两类各计一天。日记累计篇数若保留，另列指标，不能与天数混用。统一晚间日记后，不再以独立回顾记录增加第三类坚持天数。

候选默认：按用户本地“记录日”统计；当前连续允许今天尚未写时从昨天起算，避免下午就提前宣布断签。Demo 依预览日期展示这一口径。**补记过去的一天，算历史覆盖日还是过去实际坚持书写日，需确认**：两者不能混成同一个不标注的“坚持天数”。建议区分内容所属日期与实际保存日期，规则确定后再命名指标。

事件有效记录是否包括仅保存未分析、撤销/删除对统计与已领成就的影响、时区修改及旧数据归类需在正式方案中明确。候选是原文保存即能计记录日、无需付费分析；这并不代表已确认新的无需模型金币奖励。未确认前不删旧成就或自动追溯回算金币。

## 5. AI 回顾规则

1. 用户主动开启时，读取本人当日事件、日记、计划实际结果、生活清单和已回答/已跳过的主题；不向模型无界发送全历史。记录只是分析材料，其中指令文字不能覆盖产品规则。
2. 先判断事实及主题覆盖，再选尚未覆盖且对用户有意义的问题；不要“已写跑步，又问今天运动了吗”，也不要换种措辞重复追问同一内容。
3. 不把“用户没有提到”推断为“用户没做”。跳过的主题本次不继续追问。已有充分内容时允许没有问题，不为了固定问题数强凑。
4. 对单篇充分表达沮丧的日记，可选新角度：“除了写下的困难，今天有没有一个稍微轻松、得到支持或觉得有希望的瞬间？想不到也没关系，可以跳过。”若已写过相关积极或支持经历，不再问同类问题；用户不想谈就结束。
5. 复盘计划时不重复要求抄完成情况。只有用户主动要求深入某件事或确有需要的澄清，才围绕它追问；避免用日记负面情绪给能力贴标签。
6. 回顾回答、AI 问题和分析分别保存、配对显示，不拼入日记正文。新增事件另有明确保存操作，复述不新增奖励。展示真实保存/分析状态和失败恢复，费用说明集中而清楚。

本机 Demo 使用有限主题关键词与虚构场景模拟上述交互，**不能证明真实模型语义去重已经实现**。应用实施需提示词、输入结构与代表性场景一起验证，不能把关键词列表当最终算法。

## 6. 目录外动态成就：可行方案，尚待确认领取细节

已有“规则累计为主、AI 发现为辅”的基础可以扩展。用户第 30 天的例子先命中已有固定项；若目录确实没有某个里程碑，才考虑新的发现型候选。

- 程序核实用户、指标、阈值、时间范围、有效来源记录和规则版本；AI 不能编造天数、从文本猜成就已完成或决定任意金币数。
- AI 可以发现有意义的模式，提出名称、说明与证据引用；程序检查证据和指标是否成立，决定是否可领取及受控奖励。单靠文案像里程碑不能发币。
- 统一语义身份，例如“本人＋diary_current_streak＋30＋相同规则/作用范围”，检查固定及发现型已领项目，不只看标题。把“连续 30 天”和“坚持一个月”改名不能领奖两次。
- 推荐沿用：自动发现 → 展示待领取建议 → 用户确认 → 成就加入个人墙并发一次金币；忽略不发。自动发现不等于每次打开页面都付费调用模型；可复用用户主动分析/回顾或明确授权的任务预算，无 Key 的确定统计照常可用。
- 成就奖励沿用既有方向为金币/徽章，不再额外发属性；金额、上限、与固定连续奖励的叠加需统一表。不得默认把旧 discovered 的 50 币用于任意新天数成就。
- 领取复用本人归属、版本、回执、事务和唯一约束；双设备/不同请求键/名称变体只能得到一笔奖励。过时结果、删除证据和晚到任务不得静默授奖。

“AI 直接把新成就加入列表”可以先加入候选列表；是否希望无需确认就点亮徽章、何时领取金币，应与用户商定，不把可行性询问当作自动发奖授权。

## 7. 代表性应用验收

| 场景 | 期望 |
| --- | --- |
| 同一天 5 条事件、2 篇日记 | 事件 1 日、日记 1 日，篇数/条数另算 |
| 仅事件、手写日记或仅打开/跳过问答 | 对应保存类型增加；未保存的问答不自动补日记天数 |
| 日记先保存，再完成一轮 AI 回顾 | 原文及版本不变；问题、回答和分析单独保存，日记日数/账目不增加 |
| 已显示问题后刷新/退出但没有回答 | 问题仍在，标尚未回答；恢复同一轮不重复复制 |
| AI 问“发生了什么”，用户答“朋友鼓励了我” | 保留确切问题与回答、顺序/来源，不能只留脱离上下文的一句话 |
| 修改日记、再次保存或重新分析 | 过去问答/分析不被覆盖；新分析另有版本，来源能追溯 |
| 连续 3 天后断一天再写 | 累计 4、最长 3；当前段按最后写入段，用户时区一致 |
| 已写运动及睡眠，计划也记同次跑步 | 不换措辞再问这些主题、不重复授奖 |
| 日记尽是沮丧，尚无轻松/支持内容 | 可邀请换角度，也可跳过/结束；不强求积极 |
| 已写支持经历或跳过该问题 | 不因重新进入回顾再次重复提问 |
| 到连续 30 天 | 优先已有固定项，不能再靠同义 AI 成就发第二份同里程碑奖励 |
| 真正目录外候选 | 核实来源及阈值后展示；忽略无发奖，重复确认最多一笔 |
| 补记、时区、删除、迁移 | 按确认后的日期和兼容策略验证，不臆改旧账 |

Demo 只验证本机虚构状态/界面。应用统计及迁移需 SQLite/PG 验证，动态领取需真实事务及竞争测试，AI 回顾需固定样例与真实模型测试分开留证。

## 8. 辅助回顾保存协议与导出

以下为可评审的实现方向，尚未修改应用模型/API：

- 原文实体保留 diary ID、正文、作者及版本；回顾 Session 关联本人、记录日、当时参考的日记版本/相关事件与计划、开始/结束时间、实际供应商/模型及配置/提示词版本。不要把一个完整聊天字符串写回原文。
- 提问实际显示时持久记录 question ID、轮次、顺序、AI 角色及原始问题；回答以关联 question ID 保存、标用户回答角色，保留时间与后续编辑版本。跳过/未回答/已回答明确区分；尚未显示的内部候选不冒充已提问记录。
- AI 分析单独关联回顾及其依据的日记/回答版本，保留模型、生成时间、成功/失败/取消状态。失败不丢原文/已有问答，不用占位分析假装真实结果；旧任务晚到不得覆盖新日记或新分析。
- 问题及用户回答做幂等保存；刷新/双击/双设备不产生重复轮次/回答。状态冲突保留输入，退出/切日后仍按本人及日归属读取，站点模型也不能跨人串聊天。
- 问答区折叠可以减少长页面，但展开后必须保留完整问题、对应回答和 AI 分析；不只展示回答摘要。只有用户原文编辑影响日记保存状态，回答保存不把日记标成已修改。
- 导出仅原文时不混入 AI；若用户选择带辅助回顾，按明确分区导出完整 AI 问题＋用户回答＋分析及时间/来源，结构化存档保留 ID/版本关联。不能导出一串没有问题的回答或把 AI 生成内容标作用户日记原文。最终格式仍遵循 Q7 待确认项。
- 旧真实历史若原先混写或只存回答，保留现状并说明来源不完整，不能猜问题或自动删“疑似 AI 内容”。旧版虚构 Demo 也不自动逆向拆已拼接正文，可重置示例体验新流程。

Demo 现有回顾 Session、问题即时保存、回答配对、脚本分析和当时日记快照只是上述交互示例，不代替真实应用的数据库、分析任务、版本或付费模型验证。
