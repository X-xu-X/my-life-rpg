## 批次 A：重判增量修订（判定输出契约）

### 背景与现状

v1.5 已把重判链路统一为“就地更新同一条判定”（id 不变、审计只增不删），但重判时 AI 仍是**整体重新生成**判定：不受补充影响的维度，加点数值、理由、依据、分析文字也可能全部变化——用户明确要求“加点以及 AI 给出的判定理由，第一次出来后就不变；提交补充后只影响部分，不受影响的地方什么都不变，分析过程大体不变只是补充修改”。

### A1 增量修订规则（改 `app/prompts/judge.py`，`build_judge_messages` 增加先前判定注入）

**注入内容**：重判（clarification / supplement 两条链路）时，把首判完整结果作为基准注入 prompt，参数如 `prior_judgment: dict | None`（含 `affected_attributes`、`analysis`、`summary`、`confidence`、`confidence_reason`）。首次判定不注入。

**修订契约（写进 prompt 的硬规则）**：

1. **默认锁定**：与用户补充内容**不相干**的维度——`delta`、`reason`、`evidence` 必须**逐字保留**首判原文，不得改写措辞、不得调整数值。
2. **可修订的两种情况**：
   - **相关**：补充内容直接涉及的维度（如补充“还拉伸了 10 分钟”→ 体能），可修订数值/理由/依据；
   - **被推翻**：补充内容推翻了原判依据的维度（如原判“熬夜到 2 点 → 健康-0.5”，补充说明“其实 23 点就睡了”），允许**撤销**该维度——撤销 = 从 `affected_attributes` 中移除，并在 `revision_notes` 写明撤销原因。
3. **允许新增**：补充内容新识别出的生活面 → 新增维度（如原判漏了运动，补充后新增体能）。
4. **analysis 分析过程结构保持**：仍为三段（要素解析 / 锚点比对 / 加权推导），以首判文字为基准，**只更新受影响部分**并在末尾追加一句本次修订说明；禁止整体重写措辞。
5. **summary / confidence / confidence_reason**：按修订后的判定情况更新；`confidence_reason` 只保留仍未解决的不确定点（已被补充解决的点删除）。
6. **新增输出字段 `revision_notes`**（字符串数组）：逐条说明本次改了什么，如
   ```
   ["新增：体能 +1（补充信息提到拉伸 10 分钟）",
    "撤销：健康 -1（原判以为熬夜，补充说明实际 23:00 入睡）"]
   ```
   若无任何修订则为空数组 `[]`。首判时恒为 `[]`。

**dispute（反驳复核）同样适用**：注入原判定，只按反驳涉及的点修订，未涉及部分逐字保留；若反驳无据维持原判，`revision_notes` 说明“维持原判的理由”。

### A2 数据与展示

- `ai_judgments` 新增列 `revision_notes JSON`（`app/models/__init__.py` + `sql/schema.sql` 同步）；**必须走 v1.4 已有的启动时自动迁移函数**（PRAGMA table_info 检查 + ALTER TABLE ADD COLUMN），严禁要求删库。
- `judge_service` 三处落库点（首判 / clarification 重判 / supplement 重判）与 dispute 落库同步存取该字段；`app/routers/judgments.py` 列表与详情接口返回该字段。
- 前端 `JudgmentList.vue`（判定中心）与 `EventForm.vue`（结果卡）：判定卡新增「本次修订」小标签区，展示最新一次非空的 `revision_notes`（无修订时不显示）；样式沿用现有 tag/muted 风格。
- 保留 v1.5 已实现的“已重判 · 第 N 次”计数展示，二者并列。

### A3 验收标准（必须实测，附 JSON 对比证据）

1. **逐字保留断言**：同一事件首判后补充一次（补充内容只涉及运动）→ 用脚本对比首判与重判的 `affected_attributes` JSON：**非运动维度的 delta/reason/evidence 必须完全一致（字符串逐字比对）**；运动维度允许变化。
2. **撤销场景**：构造首判含“健康 -1（熬夜依据）”，补充说明实际早睡 → 重判后该维度消失且 `revision_notes` 含撤销说明。
3. **新增场景**：首判无运动维度，补充“还拉伸了 10 分钟” → 重判新增体能维度并在 revision_notes 说明。
4. **analysis 稳定性**：重判前后三段结构一致，未受影响段落文字一致，末尾有修订说明；不得整段重写。
5. **dispute 场景**：反驳无据 → 维持原判 + revision_notes 说明；反驳有据（涉及某维度） → 仅该维度变化，其余逐字保留。
6. 全流程用真实 DeepSeek 调用完成（不接受仅 mock），报告实测样例。

## 批次 B：前端体验

### B1 成功反馈改为“保留式状态”（`frontend/src/components/JudgmentList.vue`）

**问题**：v1.5 A2 已实现成功轻提示（12px 绿字、2 秒自动消失，L373-378），但实测用户总是错过——字号小、2 秒即逝、且提交后列表重渲染干扰视线。

**方案**：
- 提交成功（补充 / 反驳 / 确认 / 删除）后，**输入框与按钮所在区域整体替换为绿色状态行**，如 `✓ 已重新判定`（补充）、`✓ 已确认入账`（确认）、`✓ 已提交反驳复核`（反驳），**不自动消失**，保留至用户在同一条判定上做下一个操作（或刷新页面/切换 tab）。
- 实现建议：用 `actionSuccess` 状态驱动，`actionTarget` 仍置空（输入框收起）→ 渲染条件为“该判定存在 actionSuccess 且用户未进行下一操作”。用户点击该判定的任意操作按钮（补充/反驳/确认/编辑/审计/删除）时清除该状态并展示正常操作区。
- 成功状态不写入 localStorage（内存态即可，刷新后消失符合预期）。
- 失败路径保持不变：就近 `actionError` 展示 + 保留已输入内容（v1.4 行为）。
- 删除/保存（编辑事件）等既有成功轻提示（顶部 notice）保留，互不冲突。

**验收**：提交补充后 → 立刻在输入框原位置看到绿色“✓ 已重新判定”，不消失；点击该判定其他按钮后状态清除并恢复正常操作区；刷新后无残留；失败时仍显示错误且输入内容保留。

### B2 手账本（TimelineView）同步折叠

**方案**：
1. **提取公共分组逻辑为 composable**：`frontend/src/composables/useDateGroups.js`——入参为带时间的数组与取值函数，输出「今天 / 昨天 / 本周更早 / 更早」四组（组头含标签、日期范围、条数）+ 展开状态（localStorage 记忆，默认只展开「今天」）。把 `JudgmentList.vue` 现有实现（L33-90 的 GROUP_KEY / groupExpanded / toggleGroup / groupIsOpen / groupedJudgments）迁移到该 composable 并改为引用，**行为与交互保持不变**（回归验证：判定中心分组/折叠/记忆/搜索自动展开均正常）。
   - 说明：只共用逻辑，不强行合并两边模板，避免回归风险。
2. **TimelineView 应用**：按同样四组分组（今天 / 昨天 / 本周更早 / 更早），每条记录默认**收起为一行摘要**：时间 + 标题 + 类别标签 + 加点概览（如 `体能 +1 · 智力 +0.5`；无加点则显示“无加点”）+ 展开指示符；点击展开显示完整详情（日记原文 / 加点明细 / 依据 / 判定分析）。
3. 保留现有搜索框：搜索命中时自动展开命中项所在分组（与判定中心一致），并高亮或直接展示命中条目详情。
4. 现有删除事件等操作按钮保留在展开区。

**验收**：手账本 20+ 条记录时首屏仅显示分组头 + 今天组摘要行；折叠状态刷新后记忆；搜索“拉伸”能命中并自动展开；展开单条可看全原文与加点依据；判定中心交互与本次改动前完全一致（回归）。
